## 二、评审范围与方法

- **范围**：`Assets/_Scripts` 全部 `.cs`（**805** 个，**36,605** 行，`find … -exec cat {} + | wc -l` 口径）。不含 `Library`、`Packages`、`Assets/Plugins` 第三方源码；`Assets/Editor` 编辑器工具按约定不纳入。测试/调试设施按第 0 节声明排除评估。
- **统计口径说明**：全项目多个 `.cs` 末尾无换行，故 `wc -l` 与编辑器「总行数」存在差异；本报告统一采用上述 `cat` 汇总口径。上一版 `Presentation` 记为 12,268，本轮 12,273，两轮同口径可直接相减（+5）。
- **方法**：
  1. 四路分域逐文件通读（数据/配置层、战斗/整局/引擎层、双表现层、全局不变量与元信息），不依赖历史摘要。
  2. 工作树全部 16 个 `.cs` 改动（15 已跟踪 + 1 新增）逐行 `git diff HEAD` 审阅；对子代理结论冲突处（P-2/P-9 严格通道异常链、`BP_StableSerum` 递减时序、`PerkBaker` 兜底）亲自读源码复核。
  3. 8 个 asmdef 的 `references` 核验——**本轮磁盘无 asmdef 改动**，依赖边与上一版一致，无环、无反向边。
  4. 反模式关键词全量 grep（15 类），命中逐条核验文件与行号，区分业务代码与测试设施；泛型调用（`FindObjectsOfType<T>`）纳入计数。
  5. 行数/命名族/超大文件统计（`>150` 行文件精确 **45** 个；最大 `UI_HandView` 532 / `StandardMapGenerator` 423 / `UI_PotionGroup` 413）。

## 三、架构总览

### 3.1 程序集依赖 DAG（无环，本轮未变）

```
  Layer5  Presentation ──────────────┐ (引用全部下层 + CommonPresentation + 外部 GUI/Spine/TMP…)
  Layer4  CommonPresentation ──────────┤ (引用 Utility/ConfigData/RuntimeData/EngineUtility/GameBattle/GameRun)
  Layer3  GameRun ─────────────────────┤ (引用 Utility/ConfigData/RuntimeData/EngineUtility/GameBattle)★
  Layer2  GameBattle ──────────────────┤ (引用 Utility/ConfigData/RuntimeData/EngineUtility)★
  Layer1  RuntimeData ──┐  EngineUtility │ (RuntimeData → Utility/ConfigData/EngineUtility；EngineUtility 仅引外部包)
  Layer0  ConfigData ──┘  Utility        (ConfigData → 仅外部序列化包；Utility → 无引用，纯叶层)
  ★ = 上一版新增的指向 EngineUtility 的向下边（EventDispatcher 下沉所需），本轮维持
```

- **无环验证**：8 个 asmdef 的 `references` 形成严格分层 DAG，无反向边、无环。工作树本轮无 asmdef / 元信息改动，依赖图与上一版一致。
- **`EngineUtility` 纯度边界**：`SceneLoadUtil.FindScope` 返回 `LifetimeScope`，asmdef 因而含 VContainer——从「纯引擎工具」变为「引擎 + DI 容器感知」。仍是向下依赖、不构成环，属边界语义变化（P-8，维持）。

### 3.2 通信模型（双层四通道）

| 通道 | 方向 | 载体 | 约定 |
| --- | --- | --- | --- |
| 上行命令 | 表现 → 域 | `BattleCommandDispatcher` / 各级 `XxxCommandDispatcher` / 统一 `RunCommandDispatcher` | **命令只入队不执行**，域侧消费（`DiscardPotionNow` 为显式声明的立即生效例外） |
| 下行事件 | 域 → 表现 | **34 个** `BE_*` 事件（`public struct : IBattleEvent`）+ 各段 `XEventDispatcher`，统一继承 `EngineUtility.EventDispatcher<T>` | 表现层只订阅、不改写；**本轮新增双异常通道**：`Register`（表现层，吞异常记日志）/ `RegisterStrict`（域侧，异常上抛，见 P-9） |
| 上行只读查询 | 表现 → 域 | `BattleQueryDispatcher`（经 `StatResolver.ResolveDamage/ResolveBlock/ResolveLoss` 与结算共用公式）+ 域内 `BattlePerkQuery` | 只读快照；`UI_HandAim` 本轮改为目标集合拷入本类复用缓冲，避免持有门面内部列表（P-3 改善） |
| 横向状态介入 | 域内部 | `Hook`：`StatHook`/`SettleHook`/`DeathGuardHook` + PerkRules 组（`SlipperyHook`/`FullBlockHook`/`BufferHook` 等 9 个） | 状态经 Hook 介入结算，数值判定与预览同源 |

**本轮通信层改动——异常策略双通道化**：`EventDispatcher<TEvent>` 的 `_handlers` 由 `List<Func<TEvent,UniTask>>` 改为 `List<(Handler, bool Strict)>`，新增 `RegisterStrict` 两重载（`:31-36`），分派时 `Invoke`（`:70-72`）按 `Strict` 决定「直接 await 上抛」还是「`InvokeSafely` 吞异常记日志」。落地点有三处：
- `CardSelectionFlow.cs:18` 的 `BE_CardSelectionRequested` 处理器改走 `RegisterStrict`；
- 新增 `GameRun/Relic/RelicDomainEventRegistrar.cs`（27 行）门面，`RelicEffect.cs:28/41` 把注入的 `BattleEventDispatcher` 包装为门面，使全部 `RE_*` 遗物的 `Dispatcher.Register`（保持原调用写法）统一转发到严格通道。门面注释自述「域侧改严格通道的唯一切换点」。

设计意图是让域反应方（遗物、选卡流程）的异常不再被静默吞掉，符合「失败路径不应无声」的方向；但承接链不完整（见 §4.3 P-9）。

**两级命令门面**：战斗内命令经 `BattleCommandDispatcher` 入队；跨段整局写操作经 `RunCommandDispatcher` 收口，写域由 `GameRun` 域服务完成（含幂等 `RewardClaimService`）。计时泵在 `SegmentSceneManager.Update`（`:63`），属表现层编排职责。
