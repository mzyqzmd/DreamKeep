## 一、结论速览

### 综合评分：**92 / 100（A−）**

一句话总纲：**十一个程序集、一张无环依赖 DAG、四通道解耦（命令上行 / 事件下行 / 只读查询 / 状态介入）；配置只读一次即烘焙为运行时对象，规则与状态只存在一处，表现层只读不回写。**

### 3.1 程序集分层（asmdef 强制，已 GUID 反解核验）

        │

        │

        ├──→ GameRest    {RT, CD, UT}    空骨架（1 个 7 行标记）
        ├──→ GameShop    {RT, CD, UT}    空骨架（1 个 7 行标记）
        │
        └──→ GameRun     {GameBattle, GameEvent, GameRest, GameShop, RT, CD, UT}   ✅ 已实现（遗物系统）

【引擎级通用件】
  EngineUtility ──→ {Utility} + UniTask
        │

### 3.3 四通道通信（表现层 ↔ 战斗逻辑）

```
① 上行·命令（玩家意图，只入队不执行）
   视图 → BattleCommandDispatcher → BattleLoop.EnqueueCommand → 等待态阶段 HandleCommand

② 下行·事件（域侧结果，struct 只读载荷）
   BattleAction.Execute → List<IBattleEvent> → BattleEventDispatcher.PlayAsync → 各视图处理器并行演出

③ 上行·只读查询（预览，无副作用，与结算同源）
   表现层 → BattleQueryDispatcher.{PreviewTargets, PreviewCardDamage, PreviewCardBlock,
                                  PreviewIntentDamage, PileCount, PileCards, GetAliveEnemies} → 直算返回

④ 横向·状态介入（规则层内横切，表现层不可见）
   BA_Damage / BA_Block → Hook.Resolve(EStatChannel, …) → 各 BattlePerk.GetModifier
   BA_SettlePerk       → Hook.Settle(timing)          → 产出 BA_Heal 等动作
```

**四通道的关键性质**：通道 ③ 与通道 ④ 共用同一份规则实现（`Hook.Resolve`），因此"卡面预览显示的伤害"与"实际结算扣的血"在结构上**不可能不一致**——本架构最值得保留的设计决策。

### 3.4 战斗流程：外驱状态机 + 两类阶段

`BattleLoop` 持有 `StateMachine<BaseState<BattleLoop>>`，但状态机本身不做推进（`Utility.StateMachine` 只持当前状态与切换去重守卫）。推进由 `BattleLoop.RunLoop` 外部驱动，阶段分两类：

| 类型 | 代表阶段 | 推进方式 |
| --- | --- | --- |
| **等待型**（`IBattleCommandReceiver`） | `BP_PlayerTurnActive`（唯一） | 只处理命令，不自动推进；推进由命令自身走宿主路由（`EndPlayerTurn`） |
| **驱动型** | 其余 7 个阶段 | `await RunAsync()` 后用 `Next` 回答去处；`Next == null` 即终态（仅 `BP_BattleFinish`） |

胜负判定在两条路径结束后统一执行，故"用最后一张牌打死最后一只敌人"当帧即进结束阶段。`BP_BattleFinish` 按被遗忘卡幂等回写卡组、广播 `BE_BattleEnded`、`EndCombat()`。

八阶段顺序：`BattleStart → PlayerTurnStart → PlayerTurnActive → PlayerTurnEnd → EnemyTurnStart → EnemyTurnActive → EnemyTurnEnd → PlayerTurnStart(循环) → … → BattleFinish`

## 七、问题清单（按优先级）

### 🔴 高优先级（架构一致性，建议本轮内决定）

**H-1｜3 个空骨架程序集 + 前向空引用（存量债）**
- 证据：`GameEvent`/`GameRest`/`GameShop` 各 1 个 7 行标记；`CommonPresentation.asmdef`/`Presentation.asmdef`/`GameRun.asmdef` 均声明对这三者的引用，全项目 `using` 次数 0。
- 影响：依赖图表达了"比实际需要更多"的约束；与 2026-09-14 共识直接冲突。
- 建议：二选一——① 删 `GameEvent`/`GameRest`/`GameShop` 三 asmdef 与目录，对应引用同步删；② 保留但显式标注"预声明、暂无消费者"。不建议维持"既保留又不说"。

**H-2｜`CommonPresentation` 经 `UI_RelicsGroup` 真实耦合 `GameBattle`+`GameRun`（命名层失真）**
- 证据：`UI_RelicsGroup.cs` 绑定 `BattleContext`(GameBattle) 与 `RelicTriggerNotifier`(GameRun)；`CommonPresentation` 名义是"跨场景纯共享库"却因此依赖两个域程序集。
- 影响：`CommonPresentation` 不再能"零域依赖"地复用到未来新场景（会连带引入战斗/跑图依赖）；与"可复用件放对层"的纪律相悖。
- 建议：将 `UI_RelicsGroup`/`UI_RelicSlot`/`UI_RelicsInfoPanel` 等遗物 HUD 下沉到 `Presentation`（或新建 `Presentation/Run`），使 CommonPresentation 仅剩真正通用的卡面/气泡/飘字/特效件。

### 🟡 中优先级（可维护性与扩展性）

**M-1｜`BattleTargetDirector` 硬编码具体客户端类型**
- 字段 `private UI_HandAim _client;`；全库 grep `IAimClient` = 0。与"瞄准是战斗通用件"设计意图不符，第二个客户端（药水/遗物）接入时必须改中间件。
- 建议：抽 `IAimClient`，或注释明确"当前单客户端，第二个出现时再抽"。

**M-2｜`UI_Enemy.Update()` 逐帧意图预览可事件化**
- 攻击意图数值仅在状态变化（`BE_PerkApplied`/`Settled`/`Removed`）或回合切换时变，可改为订阅这些事件刷新。

**M-3｜分派表缺 `default` 报错，"忘加 case"静默失效**
- 位置：`Hook.Settle`/`Hook.GetModifier`/`CardModelBaker.ToRuntime`/`IntentBaker.ToRuntime`/`PerkBaker.Bake` 均为 `_ => null`/中性。`RelicBaker` 同样按类型 `switch`（`RE_*` 漏登记 → 遗物静默无效果）。
- 建议：至少在 `PerkBaker.Bake`/`CardModelBaker.ToRuntime`/`IntentBaker.ToRuntime`/`RelicBaker` 的 `_` 分支 `Debug.LogError`。

**M-4｜`CardModelBaker.IndexOfPerkAffix` 为读 `Type` 临时 `Bake` 实例（反模式）**
- 为求运行时类型调用 `PerkBaker.Bake(perk_)?.GetType()`——专门烘出一实例只为读 `Type`，既浪费又易读错。
- 建议：直接比较 `perk_.GetType()`（配置 `SO_Perk` 子类）与 `CA_ApplyPerk.Perk` 对应配置类型，或维护一张显式 SO→Runtime 类型映射。

**M-5｜`UI_CardBattle`(366)/`UI_CardFace`(258) 体量偏大**
- 影响：可维护性，非正确性。协作契约清晰，属"可接受但可改善"。

### 🟢 低优先级（整洁度）

**L-1｜`UI_OneShotVfx` 用 `_clip.name` 当 Animator 状态名**（魔法字符串）——动画状态改名即静默失效；建议显式状态名常量或 `Animator.StringToHash` 并在 Inspector 暴露。

**L-2｜残留 debug 占位串**——`EI_Mixed.GetIntentName/GetDescription` 返 `"能看到这个意图说明游戏有bug"`；`UI_PileCardsView` 兜底 `"如果游戏中看到这句话说明游戏有bug"`。应改正式文案或断言。
