> 纯架构评审文档。评审范围为 `Assets/_Scripts` 下全部 **217** 个 C# 源文件（**9684** 行），
> 数据采集于 2026-10-23 工作树状态（相对 2026-10-19 的 202 文件 / 8728 行，净增 **15 文件 / 956 行**，

## 一、结论速览

### 综合评分：**92 / 100（A−）**

一句话总纲：**十一个程序集、一张无环依赖 DAG、四通道解耦（命令上行 / 事件下行 / 只读查询 / 状态介入）；配置只读一次即烘焙为运行时对象，规则与状态只存在一处，表现层只读不回写。**

**评分相对 2026-10-19（93 / A）下调 1 分**，原因不在代码质量退步，而在**程序集边界扩张的方式**：

| 变化 | 方向 | 说明 |
| --- | --- | --- |
| 拆出 `EngineUtility` | ✅ 净收益 | 引擎级通用件（池/补间/几何/悬停执行器）脱离业务程序集，可被未来任意场景复用 |
| 拆出 `CommonPresentation` | ✅ 净收益 | 牌面、说明气泡、数字飘字、一次性特效成为跨场景可复用件；`Presentation` 首次有了"下游可复用层" |
| 铺开 4 个空骨架程序集 | ⚠️ 有争议 | `GameEvent` / `GameRest` / `GameRun` / `GameShop` 各自只有 1 个 7 行占位标记，但 `CommonPresentation` 与 `Presentation` 已对它们全部声明引用且零使用 |
| 存量技术债 | ➖ 未变 | `BattleEventDispatcher` 缺 `Unregister`、部分表现层单体超 150 行、少量死代码 |

**核心判断**：这是一次真实的架构升级（可复用边界首次从"战斗场景"下移到"引擎级 + 跨场景表现级"），但代价是**程序集声明先于真实需要**——11 个程序集里只有 7 个有实质代码，且已出现 3 处"引用了却用不上"的依赖。这与本项目 2026-09-14 自己确立的原则（*程序集数量 = 需强制的依赖方向数，不按玩法系统预开程序集*）直接冲突，故按"扣 1 分、列为最高优先级讨论项"处理。

### 3.3 四通道通信（表现层 ↔ 战斗逻辑）

```
① 上行·命令（玩家意图，只入队不执行）
   视图 → BattleCommandDispatcher → BattleLoop.EnqueueCommand → 等待态阶段 HandleCommand

② 下行·事件（域侧结果，25 个 struct 只读载荷）
   BattleAction.Execute → List<IBattleEvent> → BattleEventDispatcher.PlayAsync → 各视图处理器并行演出

③ 上行·只读查询（预览，无副作用，与结算同源）
   表现层 → BattleQueryDispatcher.{PreviewTargets, PreviewCardDamage, PreviewCardBlock,
                                  PreviewIntentDamage, PileCount, PileCards, GetAliveEnemies} → 直算返回

④ 横向·状态介入（规则层内横切，表现层不可见）
   BA_Damage / BA_Block → Hook.Resolve(EStatChannel, …) → 各 BattlePerk.GetModifier
   BA_SettlePerk       → Hook.Settle(timing)          → 产出 BA_Heal 等动作
```

**四通道的关键性质**：通道 ③ 与通道 ④ 共用同一份规则实现（`Hook.Resolve`），因此"卡面预览显示的伤害"与"实际结算扣的血"在结构上**不可能不一致**——这是本架构最值得保留的设计决策。

### 3.4 战斗流程：外驱状态机 + 两类阶段

`BattleLoop` 持有 `StateMachine<BaseState<BattleLoop>>`，但**状态机本身不做推进**（`Utility.StateMachine` 只持当前状态与切换去重守卫）。推进由 `BattleLoop.RunLoop` 外部驱动，阶段分两类：

| 类型 | 代表阶段 | 推进方式 |
| --- | --- | --- |
| **等待型**（`IBattleCommandReceiver`） | `BP_PlayerTurnActive`（唯一） | 只处理命令，不自动推进；推进由命令自身走宿主路由（`EndPlayerTurn`） |
| **驱动型** | 其余 7 个阶段 | `await RunAsync()` 后用 `Next` 回答去处；`Next == null` 即终态（仅 `BP_BattleFinish`） |

胜负判定在**两条路径结束后统一执行**，故"用最后一张牌打死最后一只敌人"当帧即进结束阶段，不必等玩家再点结束回合。这是"当帧结算"重构（提交 `6d0dd98`）的直接成果。

八阶段顺序：`BattleStart → PlayerTurnStart → PlayerTurnActive → PlayerTurnEnd → EnemyTurnStart → EnemyTurnActive → EnemyTurnEnd → PlayerTurnStart(循环) → … → BattleFinish`

## 四、分模块逐文件分析

> 说明：同构族（`AD_*` / `CA_*` / `UD_*` / `EI_*` / `BA_*` / `BE_*`）以"族"为单位给出共同模式，并**完整列出全部成员**，不抽样、不省略。

### 4.1 Utility — 7 文件 / 230 行

零业务知识的纯 C# 层，只依赖 `System`。这是全项目最"可移植"的目录，理论上可整体搬到任何 C# 工程。

| 文件 | 行 | 职责与评价 |
| --- | ---: | --- |
| `FSM/IState.cs` | 9 | `Enter()` / `Exit()` 两方法契约。极简，无冗余 |
| `FSM/BaseState.cs` | 14 | `BaseState<T> where T : class`，持宿主引用，两方法虚空实现 |
| `FSM/StateMachine.cs` | 22 | **只持当前状态 + 切换去重守卫**（`EqualityComparer`），注释明确"不内嵌帧驱动与自决切换逻辑"。这是本周期内最有价值的一次"职责收缩"——状态机不再兼任调度器 |
| `Pool/ObjectPool.cs` | 63 | 纯 C# 对象池。`Stack<T>` + 创建回调 + 取/还回调 + 上限；归还时**先复位后入栈**，超限丢弃交 GC。注释点明与 `MonoObjectPool` 的分工边界 |
| `Random/Rng.cs` | 30 | 确定性随机源（种子驱动），`Next` 三个重载 + `Pick`。用途明确：无头模拟与存档回放可复现 |
| `Stat/StatModifier.cs` | 30 | 一条修正：`additive` / `multiplier` / `floor` / `cap`。**`Neutral` 是静态属性而非 `default`**，注释直接写明原因："struct 的 cap 默认是 0，会把值钳成 0"——典型踩坑记录 |
| `Stat/ModifiableStat.cs` | 74 | 可修正数值引擎。`Value` 每次现算（加值累加 → 乘率连乘 → 上下限折叠 → 截断）；`_modifiers` 懒分配；`Reset` 支持池化复用（`Clear` 不置空以保留容量）；`Clone` 深拷贝修正列表 |

**评价**：无一文件超 80 行，职责边界锐利。`ModifiableStat` 的"池化求值"设计使 `Hook.Resolve` 在稳态下零分配。

**留意**：`StatModifier.IsNeutral` 用 `Math.Abs(multiplier - 1f) < float.Epsilon` 判中性。`float.Epsilon` 是**最小正非零 float**（约 1.4e-45），用它做相等容差在数值上近乎"精确相等"，对 `1f - ratio` 这类计算不构成误判（因为 `ratio` 是配置常量），但语义上不如显式 `1e-6f` 严谨。属风格问题，非缺陷。

**这是本报告最主要的架构分歧点**，需分两面看：

**支持方（已实现的好处）**：
- 依赖方向在**编译期**就被锁死。`GameRun → GameBattle` 一旦成立，将来写跑图系统时若有人反向引用，编译器直接拒绝，不必等代码评审发现。
- 空程序集迫使 Unity 立即生成程序集，避免"第一次加代码时 asmdef 才生效"导致的一次性意外。

**反对方（实际付出的代价）**：
- **与既有共识冲突**：2026-09-14 的架构共识原文是 *"程序集数量 = 需强制的依赖方向数，不按玩法系统开程序集——未来跑图＝一个域（`GameRun`，第一个跑图系统开写时再建）"*。当前实现把 4 个域一次性开出，**在没有任何第一个消费者的情况下**。
- **依赖声明宽于实际需要**：`CommonPresentation.asmdef` 与 `Presentation.asmdef` **都声明了对 `GameEvent` / `GameRun` / `GameRest` / `GameShop` 的引用**，而全项目对这四个命名空间的使用次数为 **0**（已 grep 核验）。`CommonPresentation` 是"跨场景可复用件"程序集，它对"跑图/商店/休息"四个未来玩法的依赖是纯投机——一旦 `GameRun` 的真实设计偏离预期，这些引用要一起改。
- **违反自身规则**：`BattleLifetimeScope` 的类注释写着 *"每条注册都必须能回答'谁要它'，答不上来即为多余"*。同一把尺子量 asmdef 引用，这 4×2 = 8 条引用答不上来。

**建议（不强制）**：若不为赶进度，可先删 `GameEvent` / `GameRest` / `GameShop` 三个 asmdef 与对应目录，仅保留 `GameRun`（它至少锁住了"战斗不认识跑图"这条最重要的方向）；`CommonPresentation` / `Presentation` 对四个骨架的引用同步删掉，等域内有真实代码再逐条加回。若因时间成本决定保留现状，则应在 README 里明确记为"预声明依赖，暂无消费者"，避免后来者误以为这些域已有实现。

## 七、问题清单（按优先级）

### 🔴 高优先级（架构一致性，建议本轮内决定）

**H-1｜4 个空骨架程序集 + 8 条无消费者引用**
- 证据：`GameEvent`/`GameRest`/`GameRun`/`GameShop` 各 1 个 7 行标记文件；`CommonPresentation.asmdef` 与 `Presentation.asmdef` 各声明 4 条对它们的引用，全项目使用次数 0。
- 影响：程序集数量从 5 涨到 11，其中 4 个无实质代码；依赖图表达了"比实际需要更多"的约束；与 2026-09-14 共识直接冲突。
- 建议：二选一——① 只留 `GameRun`，删其余三个及对应 8 条引用；② 保留但在 README 与 asmdef 注释里显式标注"预声明，暂无消费者"。**不建议维持"既保留又不说"的现状**。

**H-2｜`BattleEventDispatcher` 缺 `Unregister`（存量债，未改善）**
- 证据：`BattleEventDispatcher.cs` 只有 `Register`×2 与 `PlayAsync`×2，无任何移除入口；`UI_Actor.Bind` 一次注册 10 条，`OnDestroy` 不反注册。
- 影响：单场战斗内每个死亡敌人留下 ~10 个闭包，持有已销毁视图的托管对象至战斗结束。无功能 bug（处理器内有 null 守卫），但是"每死一个敌人滞留一组闭包"的确定性问题。
- 建议：加 `Unregister<TEvent>(handler)`（需保留委托引用，故 `Register` 应返回注册句柄）；`UI_Actor.OnDestroy` 按句柄批量反注册。

### 🟡 中优先级（可维护性与扩展性）

**M-1｜`BattleTargetDirector` 硬编码具体客户端类型，与"瞄准是通用件"的设计意图不符**
- 证据：字段 `private UI_HandAim _client;`，`BeginAim(UI_HandAim)` / `EndAim(UI_HandAim)`。全库 grep `IAimClient` = 0 命中。
- 影响：当前唯一客户端无痛，但接入第二个客户端（药水/遗物）时必须改中间件本身。而上一版 README 已把这层抽象当成既成事实描述，构成**文档与实现脱节**。
- 建议：抽 `IAimClient`（`IsAiming` / `UsesPointerTargeting` / `AimOrigin` / `ArrowShown` / `PreviewTargets` / `ApplyAimResult`），或明确在注释里写下"当前单客户端，第二个出现时再抽"。

**M-2｜三处"声明但未使用"的依赖**
- `Utility.asmdef → UniTask`：`Utility` 下 0 处 `UniTask` 使用（该层是纯 C#，无异步）。
- `Presentation.asmdef → Unity.Mathematics`：全库 0 处 `Unity.Mathematics` / `using Unity.Math`。
- 附带：`BattleLifetimeScope` 里 `builder_.RegisterInstance(battleContext)` 的注释写着"预留：供 HUD 等视图 `[Inject]` 读取血量 / 能量"，但**当前无任何 `[Inject]` 消费者**——违反组合根自己定的"答不上来谁要它即为多余"。

**M-3｜`UI_Enemy.Update()` 的逐帧意图预览可事件化**
- 证据：`RefreshIntentPreviews()` 每帧调 `_intentGroup.RefreshPreviews()` → 每个攻击图标 `PreviewIntentDamage()` → `Hook.Resolve()`。而攻击意图数值只在状态变化（`BE_PerkApplied`/`BE_PerkSettled`/`BE_PerkRemoved`）或回合切换时变。
- 影响：纯算力损耗（量级小），但把"事件驱动"的一致性削弱了一处。
- 建议：改为订阅上述三条事件 + `BE_TurnStarted` 时刷新。

**M-4｜分派表缺 `default` 报错，"忘加 case"是静默失效**
- 位置：`Hook.Settle`（switch 只有 `BP_Regen`，无 default）、`Hook.GetModifier`（`_ => Neutral`）、`CardModelBaker.ToRuntime`（`_ => null`）、`IntentBaker.ToRuntime`（`_ => null`）、`PerkBaker.Bake`（`_ => null`）。
- 影响：新增状态/词条/意图时漏登记 → 资产存在、描述正常、效果不触发，且无任何报错。
- 建议：至少在 `PerkBaker.Bake` / `CardModelBaker.ToRuntime` / `IntentBaker.ToRuntime` 的 `_` 分支 `Debug.LogError`（这三处一旦返回 null，表现是"卡上的词条凭空消失"，最难查）。

**M-5｜`UI_CardBattle`（366 行）与 `UI_CardFace`（258 行）体量偏大**
- 说明：`UI_CardBattle` 承担"选脸转发 / 姿态通道 / 拖拽 / 悬停交接 / 补间通道 / 预览对账"六件事，`#region` 已分区但边界仍可再切一刀（姿态通道 + 补间通道可合并为 `CardPose`）。
- 影响：可维护性，非正确性。当前协作契约清晰，属"可接受但可改善"。

### 🟢 低优先级（整洁度）

**L-1｜`CardSorter.SortByCost` 零调用点**——定义完整（含稳定排序与无费用卡兜底），但全库无调用者。属"为将来准备的公开 API"，可保留但在注释里标注"当前无消费方"。

## 八、确认但**不构成**问题的事项

为避免误导后续维护，以下曾被怀疑、经核验为**设计正确**：

1. **`BattleLoop` 在 `RunLoop` 里 `while(true)` 且命令队列空时立即 `return`** — 无忙等：`EnqueueCommand` 每次入队都重新拉起循环，`_loopRunning` 守卫保证单一实例。
2. **`BP_PlayerTurnEnd` 在玩家死亡时提前 `return`** — 推进由 `BattleLoop` 的 `IsBattleOver` 统一兜底，正确（但见 §4.5.2 的留意）。
3. **`BA_SettlePerk` 内直接 `Execute` 嵌套动作** — 有意为之：只合事件不进队列，避免队列重入；注释已声明。
4. **`Hook` 里的 `static readonly ObjectPool<ModifiableStat>`** — 不是单例：它不持有任何游戏状态，只是求值临时容器的复用池，且 `Resolve` 同步不可重入。
5. **`Creature.CurrentHp` / `Block` 有公开 `set`** — 看似破坏封装，但写入点已全部收敛在 `BA_*` 内，且 `BattleContext` 注释明确"变更一律由动作经动作系统写入"。收紧为 `internal set` 会更安全，属可选改善而非缺陷。
6. **`UI_HandView` 454 行** — 服务面（~15 个 `internal` 成员）虽多，但全是**读侧查询**与"单点写入"转发，无规则判断。长度来自手牌区的固有复杂度，不是职责堆叠。
7. **`LifetimeScope` 里的 `FindObjectsOfType`** — 组合根在装配期一次性扫描，属 DI 容器本应做的事。
8. **`BattleEventDispatcher` 的多处理器并行 `WhenAll`** — 意图明确（一波演出同时开播），且分派期不增删处理器（注册只发生在注入期），无并发修改风险。
9. **`BattleQueryDispatcher.GetAliveEnemies` 每次新建 `List<Creature>`** — 该接口只在瞄准期间每帧调用一次（非每手牌每帧），当前量级可忽略；若要优化可改为填充式重载（`PileCards` 已是该形态）。
