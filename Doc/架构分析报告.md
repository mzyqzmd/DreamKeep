## 一、结论速览

### 综合评分：**93 / 100（A）**

一句话总纲：**五个程序集、一张无环依赖 DAG、四通道解耦（命令上行 / 事件下行 / 只读查询 / 状态介入）；配置只读一次即烘焙为运行时对象，规则与状态只存在一处，表现层只读不回写。**

相对 2026-10-15 评审（91 / A）的核心变化（本次新增/收口，均经逐文件复核确认）：

- **状态（Perk）数值系统全面落地**——这是上次评审标注的「最大功能缺口」已被闭环：`BA_Damage` / `BA_Block` 经新增的 `Hook.Resolve(EStatChannel, …)` 求最终值，**力量 / 虚弱 / 易伤** 三类状态实现 `GetModifier`，从此真实影响伤害与格挡；`BA_SettlePerk` + `Hook.Settle` 让 **再生** 在回合边界结算为 `BA_Heal`，敌我共用。`ModifiableStat` 重写为「加值 + 乘率 + 上下限折叠」引擎并支持对象池化与克隆。
- **状态被改造为数据驱动**：配置侧 `SO_Perk`（抽象资产）+ 5 个具体 `SO_*`（力量/敏捷/再生/易伤/虚弱）；运行时 `BattlePerk` / `BP_*` 整体从 `ConfigData` 迁入 `RuntimeData`，并新增 `PerkBaker` 烘焙。设计师可在 Inspector 直接增删状态资产。
- **卡牌升级子系统全链路打通**（上次「已建模未接线」）：`ConfigData` 新增 `UpgradeData` 抽象 + `UD_*` 四种补丁 + `EUpgradeChannel`；`CardModelBaker` 在烘焙期把升级补丁解析为 `CM_ValuePatch` 运行时补丁；`CM_Runtime.Upgrade()` 现改数值 / 追加词条 / 移除词条；`CardModel.Upgrade()` 与 `UI_CardFace.Upgrade()` 已存在调用点。
- **新增第三通信原语「只读查询门面」`BattleQueryDispatcher`**：表现层唯一的只读提问出口，不入队、无副作用，预览与结算共用同一份规则（`PreviewTargets` / `PreviewCardDamage` / `PreviewCardBlock` / `PreviewIntentDamage` / `PileCount` / `GetAliveEnemies`）。通信模型由「三段式」升级为「命令上行 / 事件下行 / 只读查询 / 状态介入」四通道。
- **新增状态介入层 `Hook`（规则层内横切）**：状态→数值修正、状态→结算动作的**唯一入口**，分派表把状态实例路由到自己的 `GetModifier` / 结算分支，池化 `ModifiableStat` 做到零分配求值。
- **飘字表现层落地**（对接 2026-10-19 导入的「受击 / 回复」美术资源）：`UI_NumberPopTip`（Rise / Toss 双形态，池化）+ `PopRoot`（战斗弹层中枢，订阅 `BE_DamageDealt` / `BE_HealthRestored` / `BE_TurnStarted` 现弹伤害 / 回血 / 格挡 / 回合横幅）。
- **最后一处场景级查找已消除**：原 `UI_HoverTip.FindFirstObjectByType<UI_PopTextRoot>()` 已移除；全代码库仅剩 **1 处** `FindObjectsOfType`，且位于 DI 组合根 `BattleLifetimeScope`（对场景内 `UI_HoverTip` 做注入装配，属组合根本职，合法）。

扣分仅剩：**少数表现层单体仍超 150 行经验线**（但均内聚、以 `#region` 分区）、**`BattleEventDispatcher` 仍缺 `Unregister`**（单位视图销毁后处理器残留在字典，靠表现层 null 检查兜住、无实际 bug）、以及**少量「已建模、正式入口未规划」的能力（功能完整性，非架构缺陷）**。

## 三、架构骨架

### 3.1 程序集分层（asmdef 强制，已用 GUID 反解核验）

项目内部共 5 个程序集，依赖关系经 asmdef `.meta` GUID 反解确认如下（箭头表示「依赖」方向）：

```
Utility ─────────────┐
ConfigData ──────────┤   （两者均为叶层，仅依赖外部包，互不为依赖）
        │            │
RuntimeData ──→ {Utility, ConfigData}
        │
GameBattle ───→ {Utility, RuntimeData, ConfigData}
        │
Presentation ─→ {Utility, RuntimeData, ConfigData, GameBattle}  (+ 8 个外部包)
```

| 程序集 | 文件数 | 行数 | 依赖（仅项目内） |
| --- | --- | --- | --- |
| `Utility` | 14 | 544 | 无（仅外部包） |
| `ConfigData` | 38 | 597 | 无（仅外部包：NaughtyAttributes / UnityEngine） |
| `RuntimeData` | 39 | 1509 | Utility, ConfigData |
| `GameBattle` | 69 | 2027 | Utility, RuntimeData, ConfigData |
| `Presentation` | 42 | 4051 | 全部四个（+ 外部包） |

**核验结论**：5 个程序集构成一张**有向无环图（DAG）**，无任何反向引用或环。`ConfigData` 是纯资产/数据层，不依赖 `Utility`（「扇形汇入」而非单链）。本次相对上次未引入任何新的项目内跨层依赖，`GameBattle` 与 `Presentation` 的依赖完全符合既有 DAG。

### 3.2 四通道通信模型（表现层 ↔ 战斗逻辑）

这是本架构最核心的解耦设计，本次相对上次**从「三段式」演进为「四通道」**（复核确认）：

```
                ┌──────────────────────────────────────────────────────┐
   ① 上行·命令    │  UI_HandView ──→ BattleCommandDispatcher              │
   （玩家意图）   │        └──→ BattleLoop.EnqueueCommand()               │   （只入队，不直接驱动）
                └──────────────────────────────────────────────────────┘
   ② 下行·事件    BattleLoop → ActionSystem.Enqueue(BA_*) → BA_*.Execute(ctx)
                 → 产出 List<IBattleEvent>
                ┌──────────────────────────────────────────────────────┐
                 │  BattleEventDispatcher.PlayAsync(events)              │   （视图经 [Inject] 订阅、并行 await）
                └──────────────────────────────────────────────────────┘
                ┌──────────────────────────────────────────────────────┐
   ③ 上行·只读查询 │ 表现层 ──→ BattleQueryDispatcher.(PreviewTargets/      │   （只读直算、不入队、无副作用）
                 │           PreviewCardDamage/PreviewCardBlock/…)       │
                └──────────────────────────────────────────────────────┘
   ④ 横向·状态介入  BA_Damage/BA_Block ──→ Hook.Resolve(...) ；BA_SettlePerk ──→ Hook.Settle(...)
                 （规则层内部：状态→数值 / 状态→结算动作的单一入口，分派表路由状态实例）
```

- **① 上行命令**：表现层唯一命令入口 `BattleCommandDispatcher`，只把语义化意图（`BC_PlayCard` / `BC_PlayerEndTurn`）入队，**绝不**直接触碰循环或改状态。
- **② 下行事件**：`BattleEventDispatcher` 持「类型 → 处理器列表」字典，按事件类型查表分派；同一事件多视图处理器**并行** `await`，未注册事件静默忽略。
- **③ 上行只读查询（新增）**：`BattleQueryDispatcher` 是表现层唯一的只读提问出口，直接转调玩法层既有 `CardAffixResolver` 与 `Hook`，**预览与结算共用同一份规则**（预览的谁就一定打到谁），视图不直接触碰战斗循环/战斗态/Hook。
- **④ 状态介入（新增，规则层内横切）**：`Hook` 把「状态如何影响数值 / 状态在何时产出动作」收敛为单一入口，分派表（`switch` on `BattlePerk` 类型）把状态实例路由到它自己的 `GetModifier` / 结算分支，未登记类型取中性值或静默跳过。

> **串行闸门仍然成立**：`BattleLoop` 用 `_loopRunning` 守卫保证同时刻仅一条循环在跑；`ActionSystem` 用 `_performing` 守卫保证动作队列串行排空，每个动作执行后**等待表现层演出完成**再进下一个。

### 3.3 数据管线（配置 → 烘焙 → 运行时）

```
SO_Card ──CardModelBaker.Bake──→ CardModel(CM_Static 只读 + CM_Runtime 可变副本 + CM_ValuePatch 升级补丁)
SO_Enemy ──IntentBaker.Bake────→ Enemy(含 List<EnemyIntent>)
SO_Perk  ──PerkBaker.Bake──────→ BattlePerk(层数可变的独立实例)
                                        │
                         CardAffixResolver.Build / EnemyIntentResolver.Build
                                        │
                                   List<BattleAction> (BA_*)
```

- **配置只读一次**：`BattleSetup.Create` 在装配期把 `SO_Card` / `SO_Enemy` / `SO_Perk` 经 `CardModelBaker` / `IntentBaker` / `PerkBaker` 烘焙成运行时对象；运行时**不持有任何 SO 引用**。
- **卡片以引用为身份**：`CardModel` 刻意不覆写 `Equals`/`GetHashCode`，按引用比较，避免引用型字典/映射静默错乱。`ToMutable()` 共享静态配置引用、只深拷贝运行时状态；原型（`isCanonical`）上除升级外的写操作一律抛异常，防止污染模板。
- **升级补丁烘焙期解析**：`CardModelBaker.ResolveUpgrade` 把 `UD_*` 升级补丁在烘焙期就解析为 `CM_ValuePatch`（通道 + 词条下标 + `StatModifier`），运行期 `CM_Runtime.Upgrade()` 只应用补丁、不回查配置——升级是一次性且不可逆的。
- **多态数据**：`AffixData`/`UpgradeData`/`IntentData`/`SO_Perk` 用 `[SerializeReference]` + `SubclassSelector` 在 Inspector 上可多态编辑；运行时各持一份 `Clone()`，杜绝多份共享同一实例。

### 3.4 战斗生命周期（外驱状态机）

`BattleLoop` 内置 `StateMachine<BaseState<BattleLoop>>`，阶段序列：`BattleStart → PlayerTurnStart → PlayerTurnActive → PlayerTurnEnd → EnemyTurnStart → EnemyTurnActive → EnemyTurnEnd → (循环) → BattleFinish`。

- `PlayerTurnActive` 是**唯一等待型阶段**（`IBattleCommandReceiver`），只在 `BattleLoop` 等待态取出命令后 `HandleCommand`；其余阶段 `RunAsync` 自动推进。
- 打不出的命令（能量不足 / 牌不在手牌 / 带「不能被打出」词条）不静默丢弃，统一广播 `BE_CardPlayRejected` 让视图退牌——**失败路径也走事件**。
- `BP_BattleFinish` 已落地「局内卡组幂等回写 + 结束事件 + 清空战斗态」，其 `HandleCommand` 仍为空实现（见 §六 缺口 1）。

## 四、分模块详细分析

### 4.1 Utility（14 文件 / 544 行）—— 引擎无关的基础件
纯工具层，不依赖任何项目程序集，分 `NoEngine`（FSM / Random / Stat / Pool）与 `Engine`（Math / Pool / UI）。

- **FSM**：`StateMachine<TState>`（32）单层状态机，持当前状态 + 切换去重守卫 + `OnStateChanged` 事件，不内嵌帧驱动——正是 `BattleLoop` 所用的状态机。
- **Random**：`Rng`（29）确定性随机源，注入式单例，洗牌/抖动/随机取敌共享，保证同种子可复现。
- **Stat（本次重写核心）**：`ModifiableStat`（73）重写为「当前值 = (基础值 + Σ加值) 逐条乘算后取整，再按各修正给定的上下限折叠（下限取最大、上限取最小）后截断」的引擎；支持 `Reset`（供对象池复用实例、稳态零分配求值）、`Clone`（升级这类永久改动必须活着进战斗）；`StatModifier`（30）携带加值/乘率/上下限。这正是状态数值系统与升级数值系统的共同底座。
- **Pool（双池）**：`MonoObjectPool<T>`（97，组件实例池：激活/父节点归属/取出复位/超上限销毁，卡牌飞行复用）+ `ObjectPool<T>`（48，纯 C# 对象池，无预制体、无归属校验，`Hook` 求值复用 `ModifiableStat`）。一对互补的池化原语。
- **UI**：`UiGeometry`（46，锚点/包含判定）、`UiTween`（48，标量补间）、`UiValueText`（24，数值着色：升高/降低/降费）、`UI_ButtonScaler`（48）、`EUiAnchor`（17 枚举）。
- **Math**：`Curve`（23）。
- **评价**：教科书级工具层，零项目依赖、纯函数/数据、可单独复用；本次新增的 `ModifiableStat` 重写与 `ObjectPool` 显著提升了上层数值/状态系统的表达力与零分配能力。

### 4.2 ConfigData（38 文件 / 597 行）—— 纯资产/数据定义层
全部为 `ScriptableObject` 或纯数据类，**不含任何逻辑**，且**不依赖任何项目程序集**（仅 NaughtyAttributes 编辑器特性 + UnityEngine）。

- `SO_Card`（31）：`[SerializeReference, SubclassSelector]` 挂 `List<AffixData>`，并新增 `Upgrades`（`List<UpgradeData>`）承载升级补丁；`CanUpdate` 标记是否可升级。
- **状态配置新增为 SO 资产**：`SO_Perk`（19，抽象基类，定义图标/显示名/结算时机，全局唯一真源）+ `SO_Dexterity`/`SO_Regen`/`SO_Strength`/`SO_Vulnerable`/`SO_Weak`（12–16，各具体资产）。相对上次的「`BattlePerk` 代码子类」是一次彻底的「代码→数据」迁移。
