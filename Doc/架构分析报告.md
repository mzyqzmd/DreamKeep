## 一、结论速览

### 综合评分：**96 / 100（A）**

一句话总纲：**八个程序集、一张无环依赖 DAG、双层四通道解耦（战斗级 + 场景段级），并在其之上新增统一的「整局级命令门面」`RunCommandDispatcher`；配置只读一次即烘焙为运行时对象，规则与状态只存在一处；六个场景阶段（先古之民 / 休息 / 战斗 / 宝箱 / 商店 / 事件）的运行时逻辑全部归位 `GameRun` 域，每段配 `PresentationBridge`（事实下行 + 命令门面上行），表现层只上发意图、订阅事实；整局进度由 `RunState` 持有，地图节点（`StandardMapGenerator`）驱动阶段叠加编排。本轮最大改善来自 `cda5277`：原两个跨层一致性缺口 K1（奖励面板直写域）/ K2（战斗外药水与计时直写域）已收口——表现层现在**只经统一命令门面上报意图**，域侧写操作（含幂等领奖）全部落在 `GameRun` 域的 `RunCommandDispatcher`/`RewardClaimService`，不变量「表现层不直写域状态」首次完整成立。**

## 二、评审范围与方法

- **范围**：`Assets/_Scripts` 全部 `.cs`（692），不含 `Library`、`Packages`、第三方源码（`Assets/Plugins`）。`Assets/Editor` 仅工具脚本，不影响运行时架构。
- **方法**：
  1. 逐模块通读骨干与全部新增/变更文件（4 个 Explore 子代理分域审阅 + 主代理核验），不依赖历史摘要。
  2. 8 个 asmdef 的 `references` 全部核验（GUID ↔ asmdef 映射逐条核对），做环路检测与方向核验；确认无新增跨程序集边。
  3. 反模式关键词全量 grep（15 类），命中逐条核验文件与行号。
  4. **MonoBehaviour 引用核验按脚本 GUID 扫场景/预制体**，不只按类名 grep（类名 grep 会漏掉 YAML 里 `m_Script: {fileID: 11500000, guid: ...}` 形态的挂载）。
  5. 行为等价类改动给出「随机流是否变化 / 事件时机是否变化 / 序列化字段是否变化」三项结论。

## 三、架构总览

### 3.1 程序集依赖 DAG（无环）

```
                     ┌───────────────┐
       ┌────────────►│  ConfigData   │◄───────────┐
       │             └───────────────┘            │
       │        ┌──────────────┐                  │
       │        │   Utility    │◄──┐              │
       │        └──────────────┘   │              │
       │             ┌─────────────┴──┐           │
       ├────────────►│  RuntimeData   │◄──┐       │
       │             └────────────────┘   │       │
       │                    │             │       │
┌──────┴────────┐    ┌──────┴───────┐     │       │
│ EngineUtility │    │  GameBattle  │◄────┤       │
└──────┬────────┘    └──────┬───────┘     │       │
       │                    │             │       │
       │             ┌──────┴───────┐     │       │
       └────────────►│   GameRun    │◄────┘       │
                     └──────┬───────┘             │
                            │                     │
                     ┌──────┴─────────────┐       │
                     │ CommonPresentation │◄──────┤
                     └──────┬─────────────┘       │
                            │                     │
                     ┌──────┴──────┐              │
                     │Presentation │◄─────────────┘
                     └─────────────┘
```

- 程序集构成（当前行数）：`Utility`(8/327) ← `ConfigData`(182/3,099) ← `RuntimeData`(76/4,524) ← `GameBattle`(97/3,072) ← `GameRun`(124/3,469) ← `CommonPresentation`(46/4,155) ← `Presentation`(125/11,926)；`EngineUtility`(34/2,190) 为引擎桥接层，被 `CommonPresentation`、`Presentation` 引用，**`RuntimeData` 是唯一反向引用它的域程序集**。
- `Utility` 零外部引用（不引 UniTask、不引 DOTween、不引 Newtonsoft），纯 C# 叶层。
- `EngineUtility` 经 `using _DreamKeep.{GameBattle|GameRun|RuntimeData|ConfigData|Utility|CommonPresentation|Presentation}` 全量扫描**零命中**，asmdef `references` 仅 `UniTask`/`DOTween.Modules`/`NaughtyAttributes.Core`/`Unity.Newtonsoft.Json`/`Unity.InputSystem`——纯引擎件、不引任何域层，已重申确认。
- `RuntimeData → EngineUtility` 的向上边维持（仅存档接口用到），已在 using 行标注约束，触发消解的条件是「出现第二个非表现层的 `EngineUtility` 消费者」。

### 3.2 通信模型

| 通道 | 战斗级 | 场景段级 | 整局级（本轮新增） |
| --- | --- | --- | --- |
| 命令上行 | `BattleCommandDispatcher` | 各段 `XxxCommandDispatcher`（Ancient/Rest/Chest/Event/Shop/Battle，均 `sealed`） | **`RunCommandDispatcher`**（常驻界面只上发意图，写局内数据/效果结算由域侧执行） |
| 事件下行 | `BattleEventDispatcher` | `SegmentEventDispatcher<TEvent>` + 6 个一行子类 | 复用 `RunState` / `Player` 的原生通知下行（命令门面不持有事件通道） |
| 只读查询 | `BattleQueryDispatcher` | 段 Loop 的只读属性 / `[Inject] RunState` | `RunCommandDispatcher` 内只读取（如药水槽越界给 `null`） |
| 状态介入 | `IBattleEvent` 订阅方（遗物/Hook） | 段 Loop 内部规则经 `RunState` 受控入口 | 领奖会话 `RewardClaimService`（`Begin`/`Claim`/`End` + 幂等 `_claimed`） |

两份下行分派器（`BattleEventDispatcher` / `SegmentEventDispatcher`）的 `Register` 两重载与 `DispatchAsync` 逐字相同，刻意不合并：`GameBattle` 不能反引 `GameRun`，唯一可落点 `RuntimeData` 会把「分派原语」塞进纯数据层。两份文件摘要已互相指路。

**`RunCommandDispatcher`（本轮新增）** 是「整局级命令门面」，与既有「场景段级 `XxxCommandDispatcher`」形成**两级命令结构**：段内交互走各自段门面，跨段/常驻交互（顶栏计时、战斗外药水、领奖）走统一门面。它只做同步转发，写域全部委托给 `RunState`/`Player`/`RewardClaimService`，自身不持有事件通道，全局刷新仍由 `RunState`/`Player` 原生通知下行。

## 六、模块逐域分析

### 6.1 Utility（8 / 327）
纯 C# 叶层，零外部项目依赖、零 UnityEngine。承载 `Rng`（确定性随机，全局同种子可复现的基石）、`ModifiableStat`（加值+乘率+上下限折叠，池化/克隆）、`StateMachine<T>`、`ObjectPool<T>`。无变化，稳定。

### 6.2 EngineUtility（34 / 2,190）
纯引擎桥接层：
- **`Input`**：`PointerInput`(58) 读 InputSystem（Pointer/Mouse.current，全判空）、`PointerCursor`(47) 光标态，均挂常驻 `GameRoot`（随 `UI_SingletonObject` 进 `DontDestroyOnLoad`），全局生效、场景切换不丢。
- **`Scene`**：`SceneLoadUtil`(52) 替代旧 `SegmentSceneLoader` 的装载逻辑，已清除 F3 假注释/死 using。

- 全量 `using` 扫描确认零域层依赖（重申维持）；3 处 `Update` 均为引擎机制（详见 §4.2）。

`PointerInput`/`PointerCursor` 基于 InputSystem，挂常驻 GameRoot，全局生效；无 Find/跨对象 GetComponent 链。

- `RewardRoller` 从战斗遭遇剥离为纯 RuntimeData，同种子可复现、多池 `CollectWeighted` 去重赋权；遗物抽取下沉至 `GameRun/RelicRoller`。

### 7.6 六场景阶段（同构零漂移）
Ancient/Rest/Chest/Shop/Event/Battle 均 `LifetimeScope` + `Loop/Session` + `PresentationBridge`，表现层严格走命令/事件上行下行，无平行机制。

### 7.7 整局命令通道（本轮新增，统一门面）
`RunCommandDispatcher`（整局级）与六段 `XxxCommandDispatcher`（段级）形成**两级命令结构**。常驻界面（顶栏计时、战斗外药水、领奖）只经统一门面上报意图，域侧写操作集中在 `RunState`/`Player`/`RewardClaimService`。该门面在 `RunLifetimeScope` 注册为实例，注入 `UI_TopBar`/`UI_PotionGroup`/`UI_RewardPanel`/`BattleEntry`/`EventEntry`，把原散在表现层的写操作收口到域侧一处，降低了跨层耦合面。
