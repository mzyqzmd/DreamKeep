## 一、结论速览

## 三、架构骨架

### 3.1 程序集分层（asmdef 强制，已 GUID 反解核验）

项目内部共 **8** 个程序集（相对 2026-10-25 的 11 个，删除 `GameEvent`/`GameRest`/`GameShop` 三个空骨架）。箭头表示"依赖"方向：

```
【叶层 / 域层：仅依赖外部包或下层域】
  Utility        （纯 C#，零 UnityEngine / 零项目内依赖）
  ConfigData     （纯资产，零执行逻辑；外部：NaughtyAttributes, SerializeReferenceExtensions）
  RuntimeData    ──→ {Utility, ConfigData}
  EngineUtility  ──→ {UniTask, DOTween}          （已无 Utility 依赖，纯引擎件）
  GameBattle     ──→ {Utility, RuntimeData, ConfigData} + UniTask
  GameRun        ──→ {GameBattle, RuntimeData, ConfigData, Utility} + UniTask   ✅ 已实现（遗物 / 奖励 / 整局 RunState）

【表现层（平级两层；Presentation 依赖 CommonPresentation 为故意设计）】
  CommonPresentation ──→ {Utility, ConfigData, RuntimeData, EngineUtility, GameBattle, GameRun} + 外部包（VContainer/UniTask/TMP/NaughtyAttributes/DOTween）
  Presentation        ──→ {CommonPresentation + 上述全部域层} + 外部包（VContainer/UniTask/TMP/InputSystem/Spine/NaughtyAttributes/DOTween）
```

> 注：`CommonPresentation` 与 `Presentation` 为**平级的表现层**，通用表现件集中在 `CommonPresentation`，各场景阶段专属表现放 `Presentation`；`Presentation` 依赖 `CommonPresentation` 是故意设计。`CommonPresentation → GameRun` 是表现层对域层的正常向下依赖（非越界）。

**核验结论：无环、无反向引用。** `GameBattle` 不反向引用任何上层程序集；`GameRun`/`CommonPresentation`/`Presentation` 单向依赖 `GameBattle` 及其下层。`CommonPresentation` 与 `Presentation` 为**平级的表现层**，`CommonPresentation` 引用 `GameBattle`（查询门面）/ `GameRun`（奖励兑现所需的域模型）均属正常的"表现层→域"向下依赖，`Presentation` 额外依赖 `CommonPresentation` 为故意设计——**DAG 中无方向性异味**。（`CommonPresentation → GameRun` 曾被误判为 H-2"越界写耦合"，经设计方澄清不成立，见 §7。）

### 3.3 四通道通信（表现层 ↔ 战斗逻辑）

```
① 上行·命令（玩家意图，只入队不执行）
   视图 → BattleCommandDispatcher → BattleLoop.EnqueueCommand → 等待态阶段 HandleCommand

② 下行·事件（域侧结果，struct 只读载荷，零 GC）
   BattleAction.Execute → List<IBattleEvent> → BattleEventDispatcher.PlayAsync → 各视图处理器并行演出
   （27 个 BE_*）

③ 上行·只读查询（预览，无副作用，与结算同源）
   表现层 → BattleQueryDispatcher.{PreviewTargets, PreviewCardDamage, …} → 直算返回

④ 横向·状态介入（规则层内横切，表现层不可见）
   BA_Damage / BA_Block → Hook.Resolve(EStatChannel, …) → 各 BattlePerk.GetModifier
   BA_SettlePerk       → Hook.Settle(timing)          → 产出 BA_Heal 等动作
```

**四通道的关键性质**：通道 ③ 与通道 ④ 共用同一份规则实现（`Hook.Resolve`），因此"卡面预览显示的伤害"与"实际结算扣的血"在结构上不可能不一致。本轮新场景阶段（Ancient/Rest/Chest/Run）的表现层同样严格走命令/事件/查询三路上行下行，未引入平行机制。

### 3.4 多场景阶段与整局层（本轮新增 Chest 为第四阶段）

原架构只有单一战斗场景；现演进为**整局层（Run）** + 四个可切换的场景阶段：

- **整局层 `RunState`**（`GameRun/Run/RunState.cs`，纯 C#）：持有 `Floor`/`Rng`/`Player` 的遗物·药水·卡组等整局状态；数值变更以 `event Action`（`GoldChanged`/`FloorChanged`）下行通知 HUD——即"事件下行"通道在跑图域的复用。`RunLifetimeScope` 注册整局常驻件。
- **阶段编排 `SegmentSceneManager`**（`Presentation/_Bootstrap/Run`，243 行）：按**场景名字符串**（`Scene_Ancient`/`Scene_Rest`/`Scene_Chest`/`Scene_Battle`）Additive 加载/卸载阶段，**无对下一阶段类型的硬引用**、非上帝协调器；靠 `_session`（BattleSession 门面）与 `RunState` 驱动流转。整局常驻靠 `RunLifetimeScope` + 叠加场景实现，**无 `DontDestroyOnLoad`**。
- **五个 `*LifetimeScope`**（Ancient/Rest/Chest/Run + 既有 Battle）：结构一致，`Configure` 内只装配本阶段类型，`Parent.Container.Resolve<RunState>()` 取整局状态；各段 scope 互不引用。
- **本轮新增「宝箱段（Chest）」**：以与既有阶段完全一致的模板落地——`ChestLifetimeScope : LifetimeScope`（`Configure` 内 `Parent.Container.Resolve<RunState>()` 取整局状态、用普通/稀有 `SO_RelicPool` 装配 `ChestSession`、漏接线装配期直接抛异常）、`ChestEntry : IStartable`（开箱演出 → 中心出遗物 → 领取 → 闪光锁定 → 等继续）、`UI_Chest`（Spine 骨骼 + 指针事件，首帧 `LateUpdate` 钉帧后早退，零轮询异味）、`UI_ChestProceedButton : UI_Button`（`[Inject] Construct(SegmentSceneManager)` 收段）。**验证：第四阶段以零结构漂移加入，证明多阶段架构的可扩展性；全段无 `GameObject.Find`/`FindObjectOfType`/跨对象强耦合。**
- **`Presentation/Event` 三构件**（`UI_EventPanel`/`UI_EventOptionItem`/`UI_EventProceedItem`，各 8–9 行）：当前**无任何代码引用**，疑似先古之民/事件叙事流的待接入 UI 构件或死代码（见 §7 L-9）。

### 3.5 战斗流程：外驱状态机 + 两类阶段

`BattleLoop` 持有 `StateMachine<BaseState<BattleLoop>>`，推进由 `BattleLoop.RunLoop` 外部驱动，阶段分两类（等待型 `BP_PlayerTurnActive` 与驱动型其余 7 个），与往期一致。本轮在战斗段组合根新增"奖励面板泊入 HUD"与"遭遇奖励注入"，仍为既有的四通道接线，未改流程骨架。
