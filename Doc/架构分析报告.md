## 一、结论速览

### 综合评分：**94 / 100（A）**

一句话总纲：**八个程序集、一张无环依赖 DAG、四通道解耦（命令上行 / 事件下行 / 只读查询 / 状态介入）；「战斗级」四通道之上又长出「场景段级」四通道；配置只读一次即烘焙为运行时对象，规则与状态只存在一处。真正的新增债务集中在「存档门面的静态可变状态 + 用类型全名做键」与「ADDITIVE 场景装载的同构片段」两处，其余为局部重复与注释时效问题。**

| 维度 | 得分 | 说明 |
| --- | ---: | --- |
| 代码组织与命名 | 9.0 / 10 | 650 文件按域分目录，命名族一致（`SO_`/`CM_`/`BP_`/`BA_`/`BC_`/`BE_`/`RE_`/`UI_`/`SE_`/`EE_`/`REE_`/`AE_`）；**34** 文件超 150 行，最大 `UI_HandView` 413、`StandardMapGenerator` 410、`UI_ShopRugPanel` 387、`UI_PotionGroup` 383、`AudioRoot` 368、`MainMenuFlow` 353，逐文件核验均为内聚单职责组件/编排器；扣分项是 `Presentation` 已破 10k 行（10,137），撞上旧决议里的拆分触发线 |
| 模块耦合度与依赖 | 9.0 / 10 | 8 个 asmdef 无环无倒挂；`GameBattle` 维持零 `UnityEngine` 使用；扣分项是 `RuntimeData → EngineUtility` 这条上一版没有的向上边（仅为存档接口与资产目录，已在 `RunState`/`RunStateRestore` 的 using 行标注用途与「不得扩大」约束） |
| 可维护性 | 9.5 / 10 | 每段独立 `*LifetimeScope` 隔离 DI；`SegmentEventDispatcher<TEvent>` + `XxxCommandDispatcher` 门面模式统一；数据驱动 + Baker 分派使内容扩充零漂移 |

## 二、评审范围与方法

- **范围**：`Assets/_Scripts` 全部 `.cs`（650）、`Assets/Editor` 全部 `.cs`（19），不含 `Library`、`Packages`、`Assets/Plugins` 第三方源码。
- **方法**：
  1. 逐模块通读骨干与全部新增/变更文件，不依赖历史摘要。
  2. 8 个 asmdef 的 `references` 全部反解为具体程序集，逐条核对方向并做环路检测。
  3. 反模式关键词全量 grep，命中逐条核验文件与行号。
  4. **MonoBehaviour 引用核验必须按脚本 GUID 扫场景/预制体**，不能只按类名 grep——类名 grep 会漏掉 YAML 里 `m_Script: {fileID: 11500000, guid: ...}` 形态的挂载（上一版「`UI_SingletonObject` 零引用死代码」就是这么误判的）。
  5. 行为等价类改动一律给出「随机流是否变化 / 事件时机是否变化 / 序列化字段是否变化」三项结论。

## 三、架构总览

### 3.1 程序集依赖 DAG（无环）

```
                     ┌───────────────┐
       ┌────────────►│  ConfigData   │◄───────────┐
       │             └───────────────┘            │
       │        ┌──────────────┐                  │
       │        │   Utility    │◄──┐              │
       │        └──────────────┘   │              │
       │             ┌─────────────┴──┐           │
       ├────────────►│  RuntimeData   │◄──┐       │
       │             └────────────────┘   │       │
       │                    │             │       │
┌──────┴────────┐    ┌──────┴───────┐     │       │
│ EngineUtility │    │  GameBattle  │◄────┤       │
└──────┬────────┘    └──────┬───────┘     │       │
       │                    │             │       │
       │             ┌──────┴───────┐     │       │
       └────────────►│   GameRun    │◄────┘       │
                     └──────┬───────┘             │
                            │                     │
                     ┌──────┴─────────────┐       │
                     │ CommonPresentation │◄──────┤
                     └──────┬─────────────┘       │
                            │                     │
                     ┌──────┴──────┐              │
                     │Presentation │◄─────────────┘
                     └─────────────┘
```

- 程序集构成：`Utility`(8 文件/318 行) ← `ConfigData`(174/2,928) ← `RuntimeData`(70/3,968) ← `GameBattle`(85/2,659) ← `GameRun`(117/3,133) ← `CommonPresentation`(48/4,345) ← `Presentation`(117/10,137)；`EngineUtility`(31/1,975) 为引擎桥接层，被 `CommonPresentation`、`Presentation` 引用，**`RuntimeData` 是唯一反向引用它的域程序集**。
- `Utility` 零外部引用（不引 UniTask、不引 DOTween、不引 Newtonsoft），是纯 C# 叶层。

### 3.2 通信模型

| 通道 | 战斗级 | 场景段级 |
| --- | --- | --- |
| 命令上行 | `BattleCommandDispatcher` | `XxxCommandDispatcher`（各段一个） |
| 事件下行 | `BattleEventDispatcher` | `SegmentEventDispatcher<TEvent>` + 各段一行子类 |
| 只读查询 | `BattleQueryDispatcher` | 段 Loop 的只读属性 |
| 状态介入 | `IBattleEvent` 订阅方（遗物/Hook） | 段 Loop 内部规则 |

两份下行分派器（`BattleEventDispatcher` / `SegmentEventDispatcher`）的 `Register` 两个重载与 `DispatchAsync` **逐字相同**，刻意不合并：`GameBattle` 不能反引 `GameRun`，唯一可落点 `RuntimeData` 会把「分派原语」塞进纯数据层。两份文件摘要已互相指路。

### 4.2 明确维持（不动，附理由）

| 位置 | 为什么不动 |
| --- | --- |
| `BattleEventDispatcher` / `SegmentEventDispatcher` 合并 | 落点只能是 `RuntimeData`（`Utility` 不引 UniTask，`GameBattle` 不引 `GameRun`），把分派原语塞进纯数据层得不偿失；两份已互指 |
