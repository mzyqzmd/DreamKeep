# 存档系统总览（Slay the Spire 2 / Godot C#）

> 调研日期：2026-11-07 ｜ 代码根：`src/Core/Saves/`（约 7,500 行）｜ 视角：**单人版**，联机同步层仅作标注
> 本文所有结论与行号均来自工程源码实读；推测与未确认项集中列在 §12。

---

## 0. 一页速览

存档系统不是「把整个游戏序列化成一个文件」，而是四层设计的叠加：

1. **按作用域拆成 6 类独立档**：账号级 2 个、档位级 4 个，各自独立读写、独立版本化、互不阻塞。
2. **运行时对象 ≠ 磁盘 DTO**：`RunState` / `ProgressState` 是运行时态，`SerializableRun` / `SerializableProgress` 是拍平的快照，二者通过 `ToSave()` / `FromSerializable()` 显式转换。
3. **模型不整体序列化，只存「ModelId + 属性袋」**：卡牌/遗物/词条/附魔只落一个类型 id 和 `[SavedProperty]` 标记的少量运行时属性，读回时按 id 重建 canonical 模型再反射注入。
4. **统一 IO 抽象 + 读写双层容错**：`ISaveStore` 屏蔽本地与云，读路径有版本迁移与 14 种状态的恢复阶梯，写路径是 `.backup` + `.tmp` + 原子替换。

核心分层的图形化版本见对话中的分层图；本文给出可直接检索的文字版与行号索引。

## 2. 分档模型：6 类档 × 2 级作用域

### 2.1 路径规则

`UserDataPathProvider.cs:13-44,51-58`：

```
user://<platform>/<userId>/profile{N}/saves/<file>
     └ steam | editor | default        └ N = 1..3（硬编码）
```

- `GetAccountScopedBasePath(null)` 返回 `user://<platform>/<userId>`，作为 `GodotFileIo.SaveDir` 的根（`SaveManager.cs:160`）。
- `GetProfileDir(id)` = `profile{id}`，modded 时多一层 `modded/`（`:41`）。
- `SavesDir = "saves"`（`:9`）。
- 账号级两档直接放在根目录（相对路径就是文件名），不带 `profileN/` 前缀。
- profile 上限写死为 3：`SaveManager.SyncCloudToLocal` 的 `for (i = 1; i <= 3; i++)`（`SaveManager.cs:357`）、`CleanupTemporaryFiles`（`:427`）。
- 旧路径 `user://<dataType>` 由 `GetLegacyPreAccountPath` / `IsLegacyPath`（`:46,60`）识别，启动时搬迁。

### 3.1 `SaveManager`（`SaveManager.cs`）

- 懒加载单例 + 测试用 `MockInstanceForTesting`（`:75-89,129-137`）。
- 构造时一次性装配 6 个 Manager 与 `MigrationManager`（`:139-149`）。
- `ConstructDefault()`（`:151-170`）：`TestMode.IsOn` → `MockGodotFileIo("user://test")`；否则 `GodotFileIo(GetAccountScopedBasePath(null))`，**若 `SteamInitializer.Initialized` 再包一层 `CloudSaveStore`**（`:161-167`）。
- `InitProfileId()`（`:172-187`）：先清临时文件，再从 `profile.save` 读 `LastProfileId`，确定档位路径并创建 history 目录。
- `SwitchProfileId()`（`:199-207`）：切档位 → 立刻 `SaveProfile()` → 发 `ProfileIdChanged`。
- 对外同时暴露大量进度查询/修改便利方法（FTUE、图鉴、Epoch、分数、解锁计数等，`:520-777`），**业务层不直接碰 DTO**。
- `Saved` 事件直接转发 `RunSaveManager.Saved`（`:115-125`）。

### 3.2 `ISaveStore`（`ISaveStore.cs:6-45`）

18 个方法：同步/异步读写（string 与 byte[]）、`FileExists` / `DirectoryExists`、删除/改名、目录遍历、创建/删除目录、清理临时文件、`GetLastModifiedTime` / `GetFileSize` / `SetLastModifiedTime`、`GetFullPath`。这是一层很干净的接口——上层完全不知道文件在本地还是云。

`CloudSaveStore`（`CloudSaveStore.cs`）读全部走本地（`:22-37`），写双写本地 + 云（`:42-96`），删除/改名/目录操作双写（`:98-136`），元数据查询只走本地（`:138-156`）。云写失败只吞 `InvalidOperationException` 并记日志，**本地文件保留**。`ICloudSaveStore` 额外提供 `HasCloudFiles` / `ForgetFile` / `IsFilePersisted` / `BeginSaveBatch` / `EndSaveBatch`。

### 4.2 核心机制：ModelId + SavedProperties 属性袋

这是全系统最值得借鉴的设计。**模型对象本身不进档**，只落「哪个模型」+「哪些运行时属性偏离了配置」：

```
SerializableCard  = Id(ModelId) + CurrentUpgradeLevel + Enchantment + Props(SavedProperties?) + FloorAddedToDeck
SerializableRelic = Id(ModelId) + Props(SavedProperties?) + FloorAddedToDeck
```

| 组件 | 位置 | 职责 |
|---|---|---|
| `[SavedProperty]` | `Runs/SavedPropertyAttribute.cs` | 标记需持久化的模型属性，可带 `SerializationCondition` 与 `order` |
| `SavedProperties.From(model)` | `Runs/SavedProperties.cs:58-191` | 反射收集被标记属性，按类型分 7 个桶：`ints / bools / strings / int_arrays / model_ids / cards / card_arrays`；类型不匹配抛 `JsonException` |
| `SavedProperties.Fill(model)` | `:257-335` | 按属性名反射写回，枚举用 `Enum.ToObject` 还原，`cardArrays` 还原为 `List` |
| `SavedPropertiesTypeCache` | `Runs/SavedPropertiesTypeCache.cs` | 静态构造时遍历 `AbstractModelSubtypes` 缓存反射结果；同时建立「属性名 ↔ net id」双向映射（供联机包按位压缩传输） |
| `SerializationCondition` | `Runs/SerializationCondition.cs` | `AlwaysSave / SaveIfNotPropertyDefault / SaveIfNotTypeDefault / SaveIfNotCollectionEmptyOrNull` |
| `SerializationConditionExtensions` | `Runs/SerializationConditionExtensions.cs:49-72` | 判定默认值/空集合是否省略 |
| `JsonSerializeConditionAttribute` | `Runs/JsonSerializeConditionAttribute.cs` | STJ 的 `JsonTypeInfo` modifier，对 DTO 顶层字段同样生效 |

读写成对出现的位置：

- `CardModel.cs:1682`（`ToSerializable()`）/ `:1695-1698`（`FromSerializable()` → `save.Props?.Fill(cardModel)`）
- `RelicModel.cs:503` / `:514-517`
- `EnchantmentModel.cs:313` / `:324-327`
- `ModifierModel.cs:105` / `:115-118`

**与项目架构备忘第 4 节的关系**：该工程「canonical（ModelDb 注册）↔ mutable（运行时克隆）两态」已经把配置和运行时数据分开了，存档只需保存 mutable 态里那些显式标记的差异字段，配置数据永不进档。这是同一套思路的自然延伸。

### 4.3 序列化配置（`JsonSerializationUtility.cs` / `MegaCritSerializerContext.cs`）

- `System.Text.Json` **源生成**，`GenerationMode = Metadata`，`WriteIndented = true`，`IncludeFields = true`，`UnmappedMemberHandling = Skip`（新版本忽略未知字段，向前兼容）。
- 注册 17 个根类型：`SerializableRun`、`SettingsSave`、`PrefsSave`、`ProfileSave`、`SerializableProgress`、`RunHistory`、`JsonObject`、`MigratingData` 列表等（`:56-72`）。
- 20 个 `SnakeCaseJsonStringEnumConverter<>`（Achievement / RelicRarity / RoomType / MapPointType / EpochState …）+ `ModelIdRunSaveConverter`（把 `ModelId` 写成字符串，`:8-24`）。
- `Options` 两个 modifier：`AlphabetizeProperties`（字段按字母序输出，便于 diff）+ `JsonSerializeConditionAttribute` 条件过滤（`:17-21,47-61`）。
- `SaveUtil.cs:14-52`：8 个 `*OrDeprecated(ModelId)`，id 找不到时回落 `DeprecatedCard/Relic/Potion/...` 占位模型，避免旧档因内容被删而整个崩掉。

### 4.4 `SerializableRun` 字段清单（`SerializableRun.cs:15-84`）

| 分组 | 字段 |
|---|---|
| 版本 | `schema_version` |
| 世界 | `acts`（含 `SavedMap`）、`current_act_index`、`visited_map_coords`、`map_point_history`、`events_seen`、`map_drawings` |
| 玩家 | `players`（HP/能量/金币/牌组/遗物/药水/RNG/odds/抓取袋/解锁态/发现列表） |
| 规则 | `modifiers`、`ascension`、`odds`、`shared_relic_grab_bag`、`rng`、`dailyTime`、`platform_type` |
| 房间 | `pre_finished_room`（用于读档后恢复未结算完的房间） |
| 时间 | `save_time`、`start_time`、`run_time`、`win_time` |
| 扩展 | `extra_fields` |

注意 `SerializableRun : ISaveSchema, IPacketSerializable`——**同一 DTO 同时服务磁盘 JSON 与联机二进制包**（`:86-162` 的 `Serialize/Deserialize`），`Anonymized()`（`:164-190`）用于上传数据时脱敏。单人版可保留前者、剔除后者。

RNG 状态、`odds`、抓取袋都进档，意味着**读档后随机序列可复现**，这是 roguelike 存档正确性的关键。

## 5. 写入路径与时机

### 5.1 写盘链路

```
业务触发
  → SaveManager.SaveRun(preFinishedRoom, saveProgress=true)      SaveManager.cs:226
      → using BeginSaveBatch()                                    :232
      → SaveProgressFile()  → ProgressSaveManager.SaveProgress()  Managers/ProgressSaveManager.cs:61
                              → Progress.ToSerializable() + 打最新 schema_version + ToJson + WriteFile(同步)
      → await CurrentRunSaveTask（若上一次未完成）               :228-231
      → RunSaveManager.SaveRun()                                 Managers/RunSaveManager.cs:73
          → 守卫：!ShouldSave 或 非 Singleplayer/Host → return   :75-78
          → RunManager.Instance.ToSave(preFinishedRoom)          :79
          → SerializeAsync(MemoryStream) → WriteFileAsync(bytes) :84-86
          → Saved?.Invoke()                                      :94
```

`SaveManager.SaveRun` 用 `CurrentRunSaveTask` 做**串行化**，避免两次存档并发覆盖同一个 run 文件（`:240-246`）。`SaveBatchScope`（`SaveBatchScope.cs`）是 `readonly struct : IDisposable`，`Dispose()` 调 `EndSaveBatch()`，最终落到 `SteamRemoteStorage.BeginFileWriteBatch/EndFileWriteBatch`；作用是**把 progress + run 合成一次云批量写**，与本地 IO 无关。另一处使用在 `RunManager.cs:1268`（一局结束时的多次写）。

### 5.2 写盘时机（单人视角）

| 时机 | 位置 | 说明 |
|---|---|---|
| 进入地图点 / 新房间 | `RunManager.cs:626,651` | **主存档点**，`saveGame` 为真时 `await SaveRun(null)` |
| 战斗胜利 | `CombatManager.cs:650-655` | `MarkPreFinished()` → `SaveRun(room, saveProgress:false)` → 更新进度 → `SaveProgressFile()`；`false` 避免重复写 progress |
| 事件房结束 | `src/Core/Rooms/EventRoom.cs:117-125` | 全部 `IsFinished` 后 fire-and-forget 存一次 |
| 一局结束 | `RunManager.cs:1266-1279` + `RunHistoryUtilities.cs:65` | `SaveBatchScope` 包住进度更新、成就、`history/<StartTime>.run` |
| 结算界面加分 | `NGameOverScreen.cs:474-476` | `CurrentScore += ...` 后立即写 progress |
| 关闭设置界面 / 改键 | `NSettingsScreen.cs:175-181`、`NInputManager.cs:478-479` | 写 settings + prefs |
| 退出游戏 | `NGame.cs:516-520` | 依次 `SaveSettings / SavePrefsFile / SaveProgressFile / SaveProfile`，然后 `Quit()` |
| 启动兜底 | `NGame.cs:247-249` + 各 Manager `LoadXxx()` | 首次启动或档损坏时立即写一份默认档 |
| 进度即时变更 | `ProgressSaveManager.cs:294,719-742` | FTUE 完成、解锁、成就撤销等，改内存即落盘，粒度很细 |

**只有 `current_run.save` 是异步写**（`RunSaveManager.cs:82-93`），其余 5 类档全部同步 `WriteFile(string)`。`forceSynchronous` 构造参数可强制 run 也同步（测试用）。

### 5.3 物理层原子写（`GodotFileIo.cs:92-107`）

```csharp
path = GetFullPath(path);
CopyBackup(path);                     // 旧文件 → path + ".backup"
using FileAccess.Open(path + ".tmp", Write) → StoreBuffer(bytes);
RenameFile(path + ".tmp", path);      // 原子替换
```

- `WriteFileAsync`（`:114-126`）走 `FileAccessStream`（把 `Godot.FileAccess` 包装成 `System.IO.Stream`）+ `.tmp` + `RenameFile`。
- 残留 `.tmp` 由 `DeleteTemporaryFiles`（`:205-222`）在 `InitProfileId()` 时清理（`SaveManager.cs:424-433`）。
- 云侧删除/改名会双写；`CloudSaveStore.SyncLocalTimestamp`（`:351-361`）在成功云写后把本地 mtime 设为云端 mtime，作为「已同步」标记。

## 6. 读取路径与容错

### 6.1 读档入口

`MigrationManager.LoadSave<T>(filePath)`（`Migrations/MigrationManager.cs:255-273`）：

1. `LoadSaveFromPath<T>(filePath)`（`:275`）→ 读文件 → `LoadWithAggressiveRecovery<T>`（`:300`）。
2. 失败则尝试 `filePath + ".backup"`（`:255-273`），成功即返回备份结果。
3. 各 Manager 拿到 `ReadSaveResult<T>` 后判断 `Success`；失败则 `CreateNewSave<T>()` / `CreateDefault()` 并**立刻写回**（如 `SettingsSaveManager.cs:33-47`、`ProgressSaveManager.cs:69-96`）。

`ReadSaveResult<T>.Success`（`ReadSaveResult.cs:9-19`）把 4 种状态视为成功：`Success`、`MigrationRequired`、`JsonRepaired`、`RecoveredWithDataLoss`。

### 6.2 恢复阶梯（`LoadWithAggressiveRecovery`，`:300-420`）

| 阶段 | 处理 |
|---|---|
| JSON 语法错误 | `RepairCommonJsonErrors`（`:448-480`）正则去尾随逗号、补 `}`/`]`，成功则递归重载、留一份 `*.pre-repair` 原文，返回 `JsonRepaired` |
| 缺 `schema_version` | `ExtractSchemaVersion`（`:210-217`）抛 `MissingSchemaVersionException` → 尝试 `InferSchemaVersionFromStructure`（`:421`，本快照直接 `return null`，见 §12） |
| 版本 > 最新 | `FutureVersion` → 尝试部分恢复 → 隔离文件 |
| 版本 < 最低支持 | `VersionTooOld` → 同上 |
| 版本介于两者之间 | `MigrateDataSequentially`（`:482-511`）逐级升级，返回 `MigrationRequired`（**不落盘**） |
| 迁移抛异常 | `MigrationFailed` → 部分恢复 → 隔离 |
| 反序列化失败 | `RecoverPartialDataFromCorruptSave`（`:426-446`）强设版本号后硬解；`SerializableRun` 明确放弃（`:428-431`，宁可丢档也不接受状态不一致） |

`ReadSaveStatus`（`ReadSaveStatus.cs:3-19`）共 14 态：`Success / JsonParseError / FileNotFound / FileEmpty / MigrationFailed / MissingSchemaVersion / FutureVersion / VersionTooOld / MigrationRequired / JsonRepaired / RecoveredWithDataLoss / FileAccessError / Unrecoverable / ValidationFailed`。

### 6.3 损坏文件隔离

`PreserveCorruptFile`（`:227-253`）→ `CorruptFileHandler.GenerateCorruptFilePath`（`CorruptFileHandler.cs:7-27`）→ 改名为：

```
<原名去扩展名>.<Unix秒>.<原因码>.corrupt
```

原因码（`CorruptFileHandler.cs:29-44`）：`JSN`(JSON) / `SCH`(缺版本) / `FUT`(未来版本) / `OLD`(过老) / `MIG`(迁移失败) / `EMP`(空文件) / `ACC`(访问错误) / `UNR`(不可恢复) / `VAL`(校验失败) / `UNK`(其他)。`ShouldPreserveCorrupt`（`MigrationManager.cs:246`）排除 `FileNotFound / Success / MigrationRequired`。

### 6.4 云同步后的陈旧档清理

`SaveManager.CleanupStaleCurrentRunSaves`（`:370-422`）：从 `current_run.save`（或 `.backup`）读 `start_time`，若 `history/<StartTime>.run` 已存在，说明这局已经结算过，删掉残留的局内档，防止读档回到已结束的一局。

## 7. 版本迁移

| 项 | 实现 |
|---|---|
| 版本载体 | 每档 JSON 的 `schema_version` 字段（`ISaveSchema`） |
| 迁移声明 | `[Migration(typeof(SaveType), fromVersion, toVersion)]`（`Migrations/MigrationAttribute.cs`） |
| 基类 | `MigrationBase<T>.Migrate()` 先 `ApplyMigration(data)` 再统一 `data.Set("schema_version", ToVersion)`（`Migrations/MigrationBase.cs:28-35`） |
| 注册方式 | **源生成静态清单** `IMigrationSubtypes`（8 个类型，`Migrations/IMigrationSubtypes.cs:13-50`）经 `Activator.CreateInstance` 注册（`MigrationRegistry.cs:12-45`）；不是程序集反射扫描 |
| 最新版本 | `DeriveAndSetLatestVersions()`（`MigrationManager.cs:41-66`）取各类型迁移 `ToVersion` 最大值，缺迁移的类型补 1 |
| 最低支持版本 | `Initialize()` 硬编码（`:28-39`）：Run **13** / Progress **21** / Settings **4** / History **8** / Prefs **2** / Profile **2** |
| 中间数据 | `MigratingData` 包装 `System.Text.Json.Nodes.JsonObject`（非 JObject），提供 `Remove / Rename / Has / GetInt / GetObject / Set / SetObject / GetRawNode` 等 |
| 升级方式 | `MigrateDataSequentially`（`:482-511`）`while (version < latest)`，用 `FromVersion == 当前` 找下一跳，**逐级单步、不跨版本直达** |
| 是否落盘 | **否**。`MigrationRequired` 只在内存升级，磁盘仍是旧版，下次 `SaveXxx()` 才覆盖（`:349-357`） |
| 构造期校验 | `IsMigrationPathValid`（`:120-136`）检查重复源 → `DuplicateMigrationException`、链断裂 → `MigrationPathGapException`，直接抛异常阻止启动 |

写盘时打版本号：各 Manager 保存前统一 `xxx.SchemaVersion = _migrationManager.GetLatestVersion<T>()`（例：`ProgressSaveManager.cs:61-67`、`SettingsSaveManager.cs:26-31`、`RunHistorySaveManager.cs:48-55`）。

具体迁移示例（真实实现在 `MegaCrit/Sts2/Core/Saves/Migrations/`）：

- `SettingsSaveV4ToV5`：`saveData.Remove("disabled_mods")` —— 删字段。
- `SerializableRunV13ToV14`：下沉到 `GetRawNode()` 直接操作 `JsonNode/JsonArray`，把 `card_pool` 迁成 `card_pools` 数组。
- 其余 6 个迁移在本快照中 `ApplyMigration` 为空，仅靠基类抬版本号（多为格式调整或占位）。

## 10. 自研可复用最小集

按依赖顺序落地，避免返工：

1. **按作用域拆档**：账号级（设置 + 当前档位 id）与档位级（偏好 / 跨局进度 / 局内 / 历史），各自独立文件、独立 `schema_version`。理由：改设置不该触碰局内档，局内高频写不该阻塞进度。
2. **DTO 与运行时模型分离**：`ToSave()` / `FromSerializable()` 显式转换，禁止直接序列化带行为、事件、节点引用的运行时对象。
3. **模型用「类型 id + 属性袋」**：`{ id, props }`，`props` 按类型分桶存被标记属性；读回时按 id 查配置表实例化 + 反射注入。配置项永不进档，新增模型不影响旧档。
4. **RNG / odds / 未结算房间进档**，保证读档可复现。
5. **版本号 + 逐级迁移清单**：每条档一个链，`[Migration(T, from, to)]`，启动时校验链完整性，迁移结果只在内存、下次保存才覆盖。
6. **原子写 + 备份**：`旧文件 → .backup`、`新内容 → .tmp`、原子 rename；启动时清 `.tmp`。
7. **读档状态枚举 + 恢复阶梯**：主档 → 备份 → JSON 修复 → 版本迁移 → 部分恢复 → 改名隔离 → 默认档重建，每步可观测（日志 + 状态码）。
8. **统一 `ISaveStore` 抽象**：本地实现先行，云/平台以后用装饰器接入，业务层零改动。
9. **写盘串行化**：用一个 `CurrentSaveTask` 串行化同一文件的异步写，避免竞态覆盖。
