# 《杀戮尖塔 2》(Slay the Spire 2) 遗物系统总览

> 基于本地反编译工程 `src/Core/**` 逐文件扫描生成，覆盖 **289 件遗物模型**（`src/Core/Models/Relics/*.cs`）与全部 9 个遗物池定义。
> 中文名/描述取自 `localization/zhs/relics.json`；数值与钩子名均来自源码，未做估算。
> 统计口径：除特别说明外，"件数"指**模型类**数量，含假遗物（Fake*）与占位遗物。

---

## 0. 结论摘要

1. **遗物的"分类"在本作里是四个正交维度**：稀有度 `RelicRarity`（8 值）、获取池 `RelicPoolModel`（7 个有效池）、运行状态 `RelicStatus`（3 值）、行为标志位（`IsUsedUp` / `HasUponPickupEffect` / `IsStackable` / `SpawnsPets` / `AddsPet` / `IsWax`+`IsMelted`）。游戏 UI 只暴露前两个，后两个是纯逻辑维度。
2. **289 件遗物全部是扁平结构**：除一个辅助选择器 `VakuuCardSelector` 外，**没有任何遗物继承另一个遗物**（289/289 直接 `: RelicModel`）。复用的手段是"钩子覆写 + `DynamicVar` 参数化"，不是继承。
3. **行为实现的唯一入口是钩子**：`AbstractModel` 暴露约 174 个 `virtual` 成员，`Hook` 静态类提供 145 个分发方法，遗物按需覆写。**没有遗物自己 `new` 事件订阅，也没有遗物持有对其它系统的直接引用**（个别特例见 §5.9）。
4. **你问的"首次未出牌就结束回合 → 额外一个回合"由 `PaelsEye`（佩尔之眼）实现**，机制是「4 个钩子协作 + `CombatManager.SwitchFromPlayerToEnemySide` 的换边判定」，不需要任何"回合状态机"改造。详见 §5.1。
5. **数量分布极不均衡**：远古遗物 92 件（31.8%）占了近三分之一，几乎全部由"古代者"事件发放；而"事件池"132 件并非稀有度，而是**发放渠道**——它把远古遗物也一并收录。

## 1. 系统分层：遗物在代码里的位置

| 层 | 类型 / 文件 | 职责 |
|---|---|---|
| 模型层 | `RelicModel : AbstractModel`（`Models/RelicModel.cs`，534 行） | 单件遗物的数据 + 钩子覆写；canonical（配置）/ mutable（运行时）两态 |
| 分类层 | `RelicRarity`、`RelicStatus`（`Entities/Relics/`） | 稀有度、运行状态两个枚举 |
| 池层 | `RelicPoolModel` + 9 个子类（`Models/RelicPools/`） | 按获取渠道划分的可获得集合；`ShouldReceiveCombatHooks => false`，池本身不参与战斗 |
| 抽取层 | `RelicGrabBag`（`Runs/`）、`RelicFactory`（`Factories/`） | 按稀有度分桶洗牌、抽牌、`IsAllowed` 过滤、跨稀有度降级、兜底 |
| 派发层 | `Hook`（`Hooks/Hook.cs`，1952 行）+ `AbstractModel` 的 174 个 virtual | 把游戏事件广播给 `IterateHookListeners()` 返回的所有监听者 |
| 实体层 | `Player._relics`、`AddRelicInternal` / `MeltRelicInternal` | 归属、插入位置、闪光订阅、蜡化/融化 |
| 命令层 | `RelicCmd`（`Obtain` / `Remove` / `Replace` / `Melt`） | 唯一合法的增删入口，负责 `AfterObtained` 回调与 GrabBag 移除 |
| 表现层 | `NRelic`、`NRelicInventory`、`NRelicCollection`、`NInspectRelicScreen` | 图标、计数、pulse/used shader 参数 |

**关键契约——监听者顺序**（`CombatState.IterateHookListeners()` / `RunState.IterateHookListeners()`）：

```
战斗内：每个生物 → 其 Powers → （若是玩家）该玩家的遗物 → 该玩家的药水 → ...
战斗外：玩家牌组的所有卡牌（含附魔）→ 遗物 → 药水 → RunModifiers → MultiplayerScalingModel
```

遗物在**能力（Power）之后、药水之前**被遍历；同一玩家的多件遗物按 `Player._relics` 的添加顺序触发。这意味着"遗物之间的连锁"优先级由**获得顺序**决定，是设计上可被玩家感知的隐性规则。

`RelicModel.ShouldReceiveCombatHooks => true`，且 `IsMelted` 为真时会被 `IterateHookListeners` 直接跳过——**"融化"不是删除，而是从监听链中摘除**，这是蜡制遗物能"留在栏位里但不生效"的实现基础。

## 2. 官方分类维度

### 2.1 稀有度 `RelicRarity`（8 个枚举值）

| 枚举值 | 中文 | 件数 | 占比 | 获取渠道 | 商店标价 |
|---|---|---:|---:|---|---:|
| `Starter` | 初始 | 10 | 3.5% | 角色初始 / 事件·宝物替换 | 999（不售） |
| `Common` | 普通 | 30 | 10.4% | 战斗奖励、宝箱、商店 | 200 |
| `Uncommon` | 罕见 | 40 | 13.8% | 同上 | 250 |
| `Rare` | 稀有 | 50 | 17.3% | 同上 | 300 |
| `Shop` | 商店专属 | 30 | 10.4% | 仅商店 | 225 |
| `Event` | 事件专属 | 35 | 12.1% | 仅事件 | 999（不售） |
| `Ancient` | 远古 | 92 | 31.8% | 古代者事件 | 999（不售） |
| `None` | 占位 | 2 | 0.7% | 不可获得（兜底/弃用） | 1 |

对应源码：`RelicRarity.cs` 8 值；价格来自 `RelicModel.MerchantCost`（`RelicModel.cs:275-286`）的 `switch` 表达式。

> **注意**：`Ancient` 不是"更高级的稀有"。它是一套独立的**发放协议**——由古代者（9 位：涅奥、佩尔、欧洛巴斯、坦克斯、瓦库、特兹卡塔拉、诺奴佩普、达弗、建筑师）在对局特定节点强制插入，绕过 `RelicGrabBag` 的稀有度分桶。所以远古遗物有 92 件却几乎不参与常规掉落。

### 2.2 获取池 `RelicPoolModel`（9 个类，7 个有效）

| 池 | 中文 | 件数 | 构成 |
|---|---|---:|---|
| `SharedRelicPool` | 共享池 | 118 | 全角色通用的掉落来源（普通 25 / 罕见 30 / 稀有 35 / 商店 25 + 远古 2 + 事件 1） |
| `EventRelicPool` | 事件池 | 132 | 事件与宝箱的发放入口；**含全部远古遗物**（90 件 Ancient 在此池）与 5 件初始遗物 |
| `IroncladRelicPool` | 铁甲战士池 | 8 | 1 初始 + 1 普通 + 2 罕见 + 3 稀有 + 1 商店 |
| `SilentRelicPool` | 静默猎手池 | 8 | 同构 |
| `DefectRelicPool` | 故障机器人池 | 8 | 同构 |
| `RegentRelicPool` | 摄政王池 | 8 | 同构 |
| `NecrobinderRelicPool` | 缚魂者池 | 8 | 同构 |
| `FallbackRelicPool` | 兜底池 | 1 | 仅 `Circlet`（头环），抽空时使用 |
| `DeprecatedRelicPool` | 弃用池 | 1 | 仅 `DeprecatedRelic`，存档兼容占位 |

每个遗物的归属由 `RelicModel.Pool` 反查（`RelicModel.cs:170`）：

```csharp
public RelicPoolModel Pool => ModelDb.AllRelicPools.First(p => p.AllRelicIds.Contains(Id));
```

即**池是"多对一"的显式名单**，不是按字段推导。**3 件遗物同时属于事件池与共享池**：`LastingCandy`（吃不完的糖）、`RazorTooth`（剃刀牙）、`SparklingRouge`（闪亮口红）。

角色池的差异化不在数量而在**解锁闸门**：每个角色池都覆写 `GetUnlockedRelics`，按 `IsEpochRevealed<XxxEpoch>()` 剔除未解锁的 3/6 号纪元遗物——这是本作"时间线解锁"系统的接入点。

### 2.4 运行状态 `RelicStatus`（3 值）

| 值 | 含义 | 表现（shader 参数） | 使用场景 |
|---|---|---|---|
| `Normal` | 正常 | `pulse=0, is_used=0` | 默认 |
| `Active` | 待触发 / 条件已满足 | `pulse=1`（呼吸高亮） | 例：佩尔之眼在回合开始且本回合尚未出牌时置 `Active` |
| `Disabled` | 已失效 | `is_used=1`（灰化） | 例：蜥蜴尾巴用掉后、南瓜蜡烛跨幕失效、玩具盒次数耗尽 |

状态由模型自行设置（`Status` setter 触发 `StatusChanged` 事件给 UI），**不是由框架统一维护**。这是很省代码的做法：遗物只需要在正确的钩子里写 `Status = …`。

### 2.5 生命周期与形态标志位

| 标志 | 覆写数 | 语义 | 代表 |
|---|---:|---|---|

### 2.6 抽取权重与降级链

`RelicFactory.RollRarity()`（`RelicFactory.cs:51-59`）——战斗奖励的稀有度掷骰：

```csharp
float num = rng.NextFloat();
return (num < 0.5f) ? RelicRarity.Common
     : (num < 0.83f) ? RelicRarity.Uncommon
     : RelicRarity.Rare;
// 普通 50% / 罕见 33% / 稀有 17%
```

`RelicGrabBag.GetAvailableDeque()` 的**降级链**（`RelicGrabBag.cs:187-202`）：

```
Shop → Common → Uncommon → Rare → (None) → _mpFallbackDequeue → FallbackRelic(Circlet)
```

即目标稀有度桶被抽空时，会**向"更稀有"方向顺延**；全部抽空则退到多人兜底队列，最后退到 `Circlet`。这解释了为什么长对局后期会拿到远超常规配比的稀有遗物，以及头环为什么可能出现在任何人的栏位里。

## 4. 机制分类（15 类，单一归属）

官方只定义了"稀有度 + 池"，但玩家和设计者真正关心的是**行为面**。以下分类由我按"主导钩子"对 289 件遗物做**单一归属**归类（每件只进一类，避免重复计数），分类依据是可覆写的钩子签名而非描述文案。

归类原则（按优先级，命中即止）：
`宠物` → `回合框架` → `死亡拦截` → `药水` → `经济` → `奖励` → `牌堆` → `出牌` → `数值修正` → `开场` → `战斗事件` → `回合节奏` → `结算` → `拾取` → `占位`

## 5. 独特机制实现剖析

以下 9 组是本作遗物里**实现方式上真正特殊**的案例——不是"效果强"，而是"需要动别人的代码"。这也是自研时最值得抄的部分。

### 5.1 额外回合：佩尔之眼 `PaelsEye`（重点）

**效果**：你在每场战斗中**第一次**没有打出任何牌就结束回合时，消耗所有手牌，然后进行一个额外回合。

#### 5.1.1 状态

只用了两个 `bool`，没有状态机：

```csharp
private bool _usedThisCombat;          // 本场战斗是否已触发过（整场只能一次）
private bool _anyCardsPlayedThisTurn;  // 本回合是否已出过牌
```

#### 5.1.2 六个钩子的分工

| 钩子 | 职责 | 源码位置 |
|---|---|---|
| `BeforeCardPlayed` | 本回合一旦出牌，`_anyCardsPlayedThisTurn = true`，并把状态从 `Active` 降回 `Normal` | `PaelsEye.cs:51` |
| `AfterSideTurnStart` | 玩家侧回合开始时，重置 `_anyCardsPlayedThisTurn = false`，状态置 `Active`（点亮呼吸光） | `PaelsEye.cs:70` |
| `ShouldTakeExtraTurn` | **纯查询**：`!UsedThisCombat && !AnyCardsPlayedThisTurn && player == Owner` | `PaelsEye.cs:85` |
| `BeforeTurnEndEarly` | 触发时先把手牌全部 `CardCmd.Exhaust` 掉（在正常弃牌之前） | `PaelsEye.cs:94` |
| `AfterTakingExtraTurn` | 确认生效后 `Flash()`、状态回 `Normal`、`_usedThisCombat = true` | `PaelsEye.cs:106` |
| `AfterCombatEnd` | 清 `_usedThisCombat`，每场战斗重置 | `PaelsEye.cs:118` |

#### 5.1.3 框架侧只有 20 行代码

关键在 `CombatManager.SwitchFromPlayerToEnemySide()`（`CombatManager.cs:904-927`）：

```csharp
_playersTakingExtraTurn.Clear();
foreach (Player player in _state.Players)
{
    if (Hook.ShouldTakeExtraTurn(_state, player))
    {
        Log.Info($"Player {player.NetId} ({player.Character.Id.Entry}) is taking an extra turn");
        _playersTakingExtraTurn.Add(player);
    }
}
list = _playersTakingExtraTurn.ToList();
SwitchSides();                                   // ← 换边
foreach (Player item in list)
    await Hook.AfterTakingExtraTurn(_state, item);
await WaitForUnpause();
await StartTurn(actionDuringEnemyTurn);          // ← 重新开一个玩家回合
```

而 `SwitchSides()`（`CombatManager.cs:929-950`）的判定只有一个条件：

```csharp
flag = _playersTakingExtraTurn.Count > 0;
if (_state.CurrentSide == CombatSide.Player && !flag)
    _state.CurrentSide = CombatSide.Enemy;    // 正常：玩家 → 敌人
else
{
    _state.CurrentSide = CombatSide.Player;   // 特例：玩家 → 玩家
    _state.RoundNumber++;                     // 回合数照样 +1
}
```

**这就是全部实现**。整条链路可以概括为：

```
玩家点结束回合
  └ EndPlayerTurnPhaseOneInternal          CombatManager.cs:766
      ├ IsPlayPhase = false
      └ Hook.BeforeTurnEnd                 → 三段式派发
          ├ BeforeTurnEndVeryEarly         → PaelsEye 之外：奥利哈钢在此挂格挡
          ├ BeforeTurnEndEarly             → PaelsEye 在此消耗全部手牌
          └ BeforeTurnEnd                  → 常规（斗篷扣、尖叫酒壶…）
  └ ReadyToBeginEnemyTurnAction
      └ AfterAllPlayersReadyToBeginEnemyTurn   CombatManager.cs:852
          ├ EndPlayerTurnPhaseTwoInternal      → Hook.ShouldFlush 弃手牌、Hook.AfterTurnEnd
          └ SwitchFromPlayerToEnemySide        → Hook.ShouldTakeExtraTurn 收集 → SwitchSides
              └ StartTurn                      → 新一轮玩家回合
```

#### 5.1.4 三个设计要点（自研最该偷的）

1. **"额外回合"被建模为"换边目标的重定向"，不是"回合流程的分支"**。`StartTurn` / `EndTurn` / `RoundNumber` / 状态清理全部复用同一套代码，没有 `if (extraTurn)` 分支散落在流程里。
2. **判定与执行分离**：`ShouldTakeExtraTurn` 是纯查询（返回 `bool`，无副作用、无 `await`），真正的状态改写放在 `AfterTakingExtraTurn`。所以它可以在任何"想知道要不要多给一回合"的位置被安全地**重复调用**（例如 UI 预览）。
3. **`RoundNumber` 在额外回合中仍然递增**。这一条让"第 2/3 回合生效"的遗物（船夹板 `HornCleat`、舵盘 `CaptainsWheel`、闪亮口红 `SparklingRouge`、佩尔之肉 `PaelsFlesh`、历石 `StoneCalendar`）无需任何特殊处理就与额外回合正确联动。
4. **多发场景被 `_playersTakingExtraTurn` 列表承接**：一个玩家触发额外回合时，`EndPlayerTurnPhaseTwoInternal` 只清理**该列表内**玩家的手牌，其它玩家正常进入敌人回合——这是联机语义，单人版等价于"只清自己"。

> **注意 `ShouldTakeExtraTurn` 的契约陷阱**：`Hook.ShouldTakeExtraTurn` 遍历 `IterateHookListeners()`，**任一监听者返回 `true` 即整体返回 `true`**（`Hook.cs:1869-1879`，短路）。所以一件遗物无法"否决"另一件遗物发起的额外回合——只能各自追加。若自研需要"互斥"语义，必须在收集阶段改成"投票制"或引入优先级。

#### 5.1.5 同类但不完全相同的三个"回合边界改写"

| 遗物 | 钩子 | 改的是什么 |
|---|---|---|
| 冰淇淋 `IceCream` | `ShouldPlayerResetEnergy` | 回合开始**不清空能量**（第 1 回合除外，避免初始能量被带走） |
| 符文金字塔 `RunicPyramid` | `ShouldFlush` | 回合结束**不弃手牌** |
| 三角铃鼓 `RingingTriangle` | `ShouldFlush` | 仅**第 1 回合**不弃手牌（`RoundNumber > 1` 才弃） |
| 坚固钳子 `SturdyClamp` | `ShouldClearBlock` + `AfterPreventingBlockClear` | 格挡**不清除**，但 `AfterPreventingBlockClear` 里把超出 10 点的部分 `LoseBlock` 扣掉——"保留上限"是**在拦截成功后做减法**实现的，不是拦截时判断 |

`SturdyClamp` 这个写法值得单独记：`ShouldClearBlock` 只回答"清不清"，容量限制则放在 `AfterPreventingBlockClear` 里用 `CreatureCmd.LoseBlock` 补一刀。**查询钩子不承担业务细节**，这是本作贯穿始终的约定。

### 5.2 出牌数量上限：天鹅绒颈圈 `VelvetChoker`

不是"禁止点击"，而是**在可打出性判定里返回 false**：

```csharp
private bool ShouldPreventCardPlay => _cardsPlayedThisTurn >= base.DynamicVars.Cards.IntValue;  // 默认 6

public override bool ShouldPlay(CardModel card, AutoPlayType _) => !ShouldPreventCardPlay;
public override Task AfterCardPlayed(...) { _cardsPlayedThisTurn++; InvokeDisplayAmountChanged(); ... }
```

同时用 `ModifyMaxEnergy` 给 +1 能量（`DynamicVars.Energy`），`BeforeSideTurnStart` 里归零计数，`ShowCounter`/`DisplayAmount` 把已用张数显示在角标上。**"限制"与"补偿"是两个独立钩子，互不感知**——这是装饰器式数值系统的典型形态。

`ShouldPlay` 被 `CardModel.CanPlay` 链调用，因此**预览态卡牌也会被正确灰化**，不需要 UI 层额外判断。

### 5.3 免死与死亡拦截：蜥蜴尾巴 `LizardTail`

```csharp
public override bool ShouldDieLate(Creature creature)
{
    if (creature != Owner.Creature) return true;
    if (WasUsed) return true;
    return false;              // 返回 false = 拦截这次死亡
}

public override async Task AfterPreventingDeath(Creature creature)
{
    Flash();
    WasUsed = true;                                    // setter 内自动 Status = Disabled
    await CreatureCmd.Heal(creature, Math.Max(1m, creature.MaxHp * Heal/100m));
}
```

三层配合：
- `ShouldDieLate` 是**晚期**判定（先让别的免死效果表态），返回 `false` 阻止死亡；
- `AfterPreventingDeath` 拿到"是我拦的"通知后才结算治疗并置 `WasUsed`；
- `IsUsedUp => _wasUsed` 派生属性让 tooltip 显示"已用尽"、`IsTradable` 自动变 `false`，UI 通过 `RelicStatus.Disabled` 灰化——**一个 bool 驱动了三条表现**。

同类还有 `Fiddle`（小提琴，`ShouldDraw` 拦截抽牌）——它证明这套钩子不只服务于"死亡"，凡是"允许/禁止"语义都走同一个模式。

### 5.4 拾取型结算：`HasUponPickupEffect` + `AfterObtained`

44 件遗物在拾取瞬间结算，全部只覆写 `AfterObtained()`：

```csharp
// 潘多拉魔盒 PandorasBox（示意结构）
public override bool HasUponPickupEffect => true;
public override async Task AfterObtained() { /* 把打击/防御全部转化 */ }
```

框架侧在 `RelicCmd.Obtain()`（`Commands/RelicCmd.cs:16-36`）里统一调用：

```csharp
player.AddRelicInternal(relic, index);
if (!relic.IsStackable) { player.RelicGrabBag.Remove(relic); runState.SharedRelicGrabBag.Remove(relic); }
relic.FloorAddedToDeck = runState.TotalFloor;
await relic.AfterObtained();     // ← 唯一入口
```

**设计含义**：`HasUponPickupEffect` 是纯粹的"声明性标志"（影响 `IsTradable` 与本地化描述口径），**真正的逻辑只在 `AfterObtained` 里**。所以"拾取型"不是一种类型，而是一种约定。

蛋系列（`MoltenEgg` / `ToxicEgg` / `FrozenEgg`）则更进一步，同时覆写四个钩子以覆盖**所有获取渠道**：

| 钩子 | 覆盖的场景 |
|---|---|
| `TryModifyCardBeingAddedToDeck` | 战斗中/事件中直接入组 |
| `TryModifyCardRewardOptionsLate` | 战后卡牌奖励 |
| `ModifyMerchantCardCreationResults` | 商店货架 |
| `IsAllowed` | 第 3 幕宝箱前才可能出现（`IsBeforeAct3TreasureChest`） |

三者共用 `EggRelicHelper.UpgradeValidCards(cards, CardType.Xxx, this)`，差异只有卡牌类型。**"一个行为 × N 个入口"用同一个 helper 收敛**，这是可复用度最高的一处。

### 5.5 蜡制遗物：玩具盒 `ToyBox` 的 `IsWax` / `IsMelted`

玩具盒是 289 件里唯一**运行时生成遗物**的设计：

```csharp
public override async Task AfterObtained()
{
    for (int i = 0; i < DynamicVars["Relics"].IntValue; i++)   // 4 件
    {
        RelicModel r = RelicFactory.PullNextRelicFromFront(Owner).ToMutable();
        r.IsWax = true;                                        // ← 打上蜡标记
        list.Add(new RelicReward(r, Owner));
    }
    await RewardsCmd.OfferCustom(Owner, list);
}

public override async Task AfterCombatEnd(CombatRoom __)
{
    CombatsSeen++;
    if (CombatsSeen % DynamicVars["Combats"].IntValue == 0)     // 每 3 场战斗
    {
        var r = Owner.Relics.FirstOrDefault(x => x.IsWax && !x.IsMelted);
        if (r != null) await RelicCmd.Melt(r);
    }
}
```

三个机制点：
1. **`IsWax` 会改写标题**（`RelicModel.Title` 里套 `ToyBox.WaxRelicPrefix`，UI 显示"蜡制的 XX"）——一个字段同时驱动数据与文案。
2. **`RelicCmd.Melt()` → `Player.MeltRelicInternal()`**：不删除、不触发 `AfterRemoved` 之外的清理，只置 `IsMelted`。而 `IterateHookListeners` 会 `Where(r => !r.IsMelted)` 跳过它 → **遗物留在栏位但静默失效**。
3. **`IsUsedUp` 是派生属性**：`CombatsSeen >= Combats * Relics`，即 4 件 × 3 场 = 12 场后玩具盒自身耗尽。派生不落存档，`CombatsSeen` 才落存档（`[SavedProperty]`）。

> 自研借鉴：**"临时/劣化版物品"不要用新类型表达，用一个形态标记 + 统一失效通道**。`IsWax`（来源）+ `IsMelted`（状态）+ `IterateHookListeners` 里的单行过滤，是成本最低的实现。

### 5.6 假遗物：`Fake*` 系列（10 件）

`FakeAnchor` / `FakeBloodVial` / `FakeHappyFlower` / `FakeLeesWaffle` / `FakeMango` / `FakeMerchantsRug` / `FakeOrichalcum` / `FakeSneckoEye` / `FakeStrikeDummy` / `FakeVenerableTeaSet`。

### 5.7 兜底与叠加：头环 `Circlet`

```csharp
public sealed class Circlet : RelicModel
{
    public override RelicRarity Rarity => RelicRarity.None;
    public override bool IsStackable => true;
}
```

- `RelicFactory.FallbackRelic` 直接指向它，抽取失败时兜底；
- `IsStackable = true` 让 `RelicCmd.Obtain` **不把它从 GrabBag 移除**，且 `IncrementStackCount` 合法；
- `Rarity = None` 让它永不被 `RelicGrabBag` 的稀有度分桶收进（`_rarities` 只含 Common/Uncommon/Rare/Shop），因此**只能通过兜底路径出现**。

一件 8 行的类，撑起了整个"池子抽空"的容错。

### 5.8 唯一的架构特例：纸蛙 `PaperPhrog` / 纸鹤 `PaperKrane`

除这两件外，所有遗物都通过 `Hook.*` 统一派发。而"易伤倍率/虚弱倍率"这类**乘区参数**没有走通用管线——`VulnerablePower` 里硬编码了具体遗物：

```csharp
// VulnerablePower.cs:34-47
decimal num = base.DynamicVars["DamageIncrease"].BaseValue;   // 1.5
if (dealer != null)
{
    PaperPhrog paperPhrog = dealer.Player?.GetRelic<PaperPhrog>();      // ← 直接点名
    if (paperPhrog != null) num = paperPhrog.ModifyVulnerableMultiplier(target, num, props, dealer, cardSource);
    CrueltyPower power = dealer.GetPower<CrueltyPower>();
    if (power != null) num = power.ModifyVulnerableMultiplier(...);
}
```

`ModifyVulnerableMultiplier` / `ModifyWeakMultiplier` **不在 `AbstractModel` 的 virtual 列表里**（grep 全工程只有 4 处声明），是一次典型的"为省一次广播而做的定点直连"。

**代价与启示**：
- 代价：`PaperPhrog` 的 `ModifyVulnerableMultiplier` **不是 `override`**，忘写方法名不会有编译错误，是静默失效的隐患；新增同类遗物必须改 `VulnerablePower`。
- 启示：自研时**乘区参数没有扩展点，就会长出硬编码**。若要给状态倍率留扩展口，正确做法是把 `ModifyXxxMultiplier` 也纳入 `IterateHookListeners` 的广播，代价是每次伤害计算多一次遍历（本作的做法是用 `Creature.Powers` 直接查具体类型规避）。

### 5.9 顺带一提：`VakuuCardSelector`——唯一的非遗物类

`Models/Relics/` 目录里唯一不继承 `RelicModel` 的类。它是 `ICardSelector` 的**确定性实现**（永远取前 N 张 / 第一张），用于 `瓦库`（Vakuu）相关事件的自动选牌，避免在 AI/测试路径上弹出玩家选择框。放在 Relics 目录属于**目录归属上的历史遗留**，不是遗物功能。

## 6. 自研可借鉴的六条结论

| # | 结论 | 依据 |
|---|---|---|
| 1 | **遗物 = 纯数据模型 + 钩子覆写，扁平不继承**。289 件遗物零继承（唯一例外是辅助选择器），复用靠 `DynamicVar` 参数化 + helper 收敛 | §2、§3、§5.4 |
| 2 | **框架侧只提供"查询钩子"和"通知钩子"两类，业务全部交给模型**。"额外回合"只改 `SwitchSides` 一个 `if`，20 行搞定 | §5.1.3 |
| 3 | **查询与执行必须分离**（`ShouldXxx` 无副作用 / `AfterXxx` 才改状态），否则每次 UI 预览都会污染存档 | §5.1.4、§5.2 |
| 4 | **"限制"用拦截钩子、"补偿"用修正钩子，两者互不感知**，不要写成一个大 `if`。`SturdyClamp` 的"保留 10 点"是在拦截成功后做减法实现的 | §5.2、§5.1.5 |
| 5 | **形态标记 > 子类**：蜡制靠 `IsWax` + `IsMelted` + 监听链一行过滤；假货靠 `Rarity` 打折；兜底靠 `IsStackable` + `Rarity=None`。新增"变体遗物"不需要新类型 | §5.5、§5.6、§5.7 |
| 6 | **乘区参数必须留扩展点**，否则必然长出 `VulnerablePower` 这种点名硬编码 | §5.8 |

**若只抄一件事**：抄 `SwitchFromPlayerToEnemySide` 的"换边重定向"写法。它让"额外回合""跳过敌人回合""连续两回合"这类需求全部退化为同一个钩子的返回值，而不需要在回合流程里到处打补丁。
